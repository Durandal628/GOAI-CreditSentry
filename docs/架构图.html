图 02

为什么是 6 个 Worker

数量不是拍出来的，是数出来的。判据两条，且可证伪：权限集不可安全合并则必须拆；目标函数相互对立则必须拆。反过来，权限相同 + 目标一致 + 失败策略一致，则必须合并。

合并 02 + 03定性者持有取证工具 → 边查边下结论的确认偏差，且 PII 触点扩散、脱敏范围失控
合并 analyst + advocate同一上下文自我质疑 → LLM 倾向自洽，对抗坍缩，质疑形同虚设
合并 04 + 05执行者自审 → 直接违反《商业银行内部控制指引》不相容职务分离

为什么不是 10？把 due-diligence 再拆成征信官／司法官／流水官，三者权限集相同、目标函数一致、失败处理策略一致——按合并判据必须合并。继续拆只增加消息跳数与 Token，不增加任何控制力。这条法则是可证伪的：只要能举出一对「权限与目标都不同却应当合并」的角色，法则就被推翻。

图 03

控制流：SOP 五阶段状态机

核心原则是一句话：LLM 只做阶段内判定，不决定流程走向。金融场景要求可复现可审计，纯 LLM 自由编排不可审计。全流程只有一条回退边，且有重试上限——不存在无限循环。

可审计性的关键落点：路由决策本身就是一条 Trace Span，携带 routing_key、命中规则 ID、规则版本三个字段。「为什么当时走了这条分支」不是靠日志拼凑推测出来的，是直接读出来的。

同一主体、完全相同的三类信号，CASE-002 的结论是 RISK_REFUTED · L0。差别只在个案细节：涉诉小额已结案且我方为原告、转出对手方是稳定供应商、法代变更在风险窗口之前。让 Agent 敢说「这不是风险」，比让它报警难得多——误杀正常客户会直接抽贷断贷。
