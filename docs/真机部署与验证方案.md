# 真机部署与验证方案

> 目标：把「声明文件写得很像」变成「集群里真的跑起来，且不变量在运行时可被证明」。
>
> 本文所有上游事实来自 `agentscope-ai/AgentTeams` 主干（HiClaw 已并入 AgentScope，仓库更名为 AgentTeams）。
> CRD 定义取自 `helm/agentteams/crds/*.yaml`，Chart 参数取自 `helm/agentteams/values.yaml`。
> **上游仍在快速迭代（v1.1.1 / 2026-05），部署当天必须重新拉一次 CRD 复核。**

---

## 0. 一句话结论

真机部署不是「把现有 YAML 拷到集群」，因为**现有 Worker CR 在真实 CRD 下是无效资源**。
真正的工作量集中在三件事，其余都是水到渠成：

1. **CR 合规化** —— 版本号、必填字段、`env` / `mcp` / `skills` 三处形状全部不同（§1）
2. **确定性状态机在真机上的落点** —— AgentTeams 的 Team Leader 是个 LLM Agent，我们的路由是确定性代码，二者必须先谈清楚（§2）
3. **工具级权限的执行点下沉** —— 真实 CRD **无法表达 per-tool 白名单**，「内控即拓扑」的执行点必须从 CR 移到网关 + MCP Server 双层（§3）

第 3 条听上去是坏消息，其实是好消息：它把原本只有单元测试背书的不变量，变成了**集群里可现场复现的拦截**。

## 1. 先修：现有 CR 与真实 CRD 不兼容

上游 CRD 组名 `agentteams.io` 我们猜对了，**版本号猜错了**，字段形状大面积不同。

### 1.1 Worker CR 逐字段对照

| 我们现在写的 | 上游 `workers.agentteams.io` 实际 | 后果 |
|---|---|---|
| `apiVersion: agentteams.io/v1` | 唯一 served 版本是 **`v1beta1`** | ❌ **拒绝**：no matches for kind |
| （未声明） | `spec.model` **required**，字符串 | ❌ **拒绝**：必填字段缺失 |
| `spec.llm.{enabled,profile,gateway}` | `spec.model` + `spec.modelProvider`（网关侧 Model API 名） | ⚠️ 需映射，`profile` 概念上游没有 |
| `spec.soul: souls/x/SOUL.md`（路径） | `spec.soul` 是 **SOUL.md 的内容字符串**（控制器据此生成文件） | ⚠️ 需内联，不能传路径 |
| `spec.env: [{name, value}, {name, valueFrom.secretKeyRef}]` | `spec.env` 是 **`map[string]string`** | ❌ 形状不同；**`secretKeyRef` 根本不可表达** |
| `spec.mcp[].{server, allowedTools[], auth, egress}` | `spec.mcpServers[].{name, url, transport}`，仅此三字段 | ❌ **`allowedTools` / `auth` / `egress` 全部无处安放** |
| `spec.skills: [{name, version, source: nacos://…}]` | `spec.skills` 是 **字符串数组且显式禁止 `^nacos://`**；远程走 `spec.remoteSkills[{source, authType, skills[{name,version,label}]}]`，`source` 必须匹配 `^nacos://host[:port]/namespace-id$` | ❌ 需拆成两个字段 |
| `spec.policy.{piiAccess, prohibited, decisionBoundary}` | 无此字段 | ⚠️ 结构化裁剪后静默丢失 |
| `spec.observability.{tracing, notes}` | 无此字段 | ⚠️ 同上 |

补充：上游还提供了我们没用但有价值的字段 —— `identity`、`agents`（生成 AGENTS.md）、`channelPolicy`（Matrix @提及的允许/拒绝名单）、`resources`、`idleTimeout`、`state: Running/Sleeping/Stopped`、`accessEntries`（对象存储/网关的云凭证 scope 声明）。

### 1.2 Team CR 对照

| 我们现在写的 | 上游 `teams.agentteams.io` 实际 |
|---|---|
| `spec.manager.{runtime, soul, responsibilities}` | 无。**Manager 是独立 CR**（`managers.agentteams.io`，同样 `required: [model]`） |
| `spec.teamLeader.worker: risk-commander` | `spec.workerMembers[].role: team_leader`，CEL 规则强制**恰好一个** |
| `spec.workers: [名字数组]` | `spec.workerMembers[].{name, role: worker}` |
| `spec.collaboration.humanInLoop.approverRoles` | `spec.admin` + `spec.humanMembers[{name, matrixUserId, role: coordinator}]` |
| `spec.routing.{table, version, source}` | **无此字段，静默裁剪** —— 路由表在上游没有归宿 |
| `spec.state.{store, concurrency, ordering}` | 无此字段 |
| `spec.invariants.*` | 无此字段 |

### 1.3 一个我们没用上的资源：Human CR

`humans.agentteams.io` 是现成的人类主体建模：`displayName`、`permissionLevel`（1=Admin / 2=Team 级 / 3=Worker 级）、`accessibleTeams`、`identitySource.{issuer, subject}`。

**这正好是我们 L2 审批环节缺的那一块。** 目前「风险经理 / 授信审批人」只是 `team.yaml` 里的两个中文字符串，真机上应该落成两个 Human CR，审批就变成真实 Matrix 账号在房间里的真实动作，而不是 PoC 里的一个布尔量。

### 1.4 修复方式

改 `tools/gen_agentteams.py`，让它输出**两种方言**：

- `--dialect upstream`（默认）：严格贴合 `v1beta1`，可 `kubectl apply`
- `--dialect annotated`：在 upstream 基础上，把 CRD 装不下的语义（`allowedTools`、`piiRedaction`、`prohibited`、`equivalence-class`）降级为 `metadata.annotations`，前缀 `creditsentry.io/`

第二种是关键：**注解不参与调度，但参与审计**。§3 的校验器从集群读回注解，与 `permissions.py` 比对，这样「CR 即权限矩阵」在真机上依然可验证，只是从 spec 挪到了 annotation。

> 真源不变：`poc/creditsentry/permissions.py` 仍是唯一权威，两种方言都从它生成。

## 2. 必须先定的架构问题：真机上谁跑状态机

这是整个部署方案里唯一有真实分歧的决定，摊开说。

**冲突点**：AgentTeams 的 Team Leader 是一个住在 Matrix 房间里的 LLM Agent，靠对话驱动协作。
我们的 `RiskCommander` 是一台确定性状态机，核心主张就是「**LLM 只做阶段内判定，不决定流程走向**」。

### 三个选项

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 全原生** | 把 11 条路由规则写进 Team Leader 的 SOUL，让 LLM 照着走 | ❌ 直接废掉核心主张。路由不再可复现、不再可举证，赛题最看重的那条没了 |
| **B. 路由即 MCP Server**（推荐） | 确定性状态机打包成第 5 个 MCP Server `sop-router`，Team Leader 的 SOUL 只写一条铁律：**任何阶段推进前必须调用 `sop-router.next()`，并且只能执行它返回的动作** | 需要新写一个 MCP Server；LLM 仍有「不调用」的可能，需靠 §3 的兜底拦截 |
| **C. 混合演示** | 基础设施上真机（房间、网关、Trace 都是真的），业务闭环仍跑 PoC 进程 | 保守退路，证据力弱一档，但必须如实标注 |

### 选 B，理由

`sop-router` 只用到 CRD 明确支持的 `spec.mcpServers[{name, url}]`，零 hack。
更重要的是它把主张变成了**可被违反、因而可被检验**的东西：

- Team Leader 若绕过 router 直接指挥 Worker → Worker 侧校验发现 `case_id` 无对应放行令牌 → 拒绝执行并落合规事件
- 于是「LLM 不决定流程」不再是一句设计声明，而是一条**能在集群里现场演示违反后被拦截**的不变量

同时 B 保留了 A 的全部好处：房间里的对话是真的，人真的能介入，Element 截图是真的。

**B 的落地增量**：`sop-router` 复用 `poc/creditsentry/routing.py` + `gate.py`，不重写逻辑，只加一层 MCP 传输壳。

## 3. 工具级权限的执行点下沉

### 3.1 问题

真实 Worker CR 只能声明「这个 Worker 能看见哪几个 MCP endpoint URL」，**没有任何 per-tool 白名单字段**。

我们权限矩阵里最有说服力的部分恰恰是工具级的：`due-diligence` 能调 `credit-core-mcp.get_exposure`，但**不能**调 `credit-core-mcp.adjust_limit`——同一个 server，不同的工具。这个粒度在 CR 里表达不出来。

### 3.2 方案：三层执行，逐层收紧

| 层 | 执行点 | 粒度 | 失败表现 |
|---|---|---|---|
| L1 可见性 | Worker CR `spec.mcpServers` | server 级 | 工具压根不在 Agent 的工具列表里 |
| L2 网关 | Higress consumer 路由 + 路径策略 | server 级 + 路由级 | HTTP 403，落 Higress access log |
| L3 服务端 | MCP Server 内 `permissions.is_allowed(caller, server, tool)` | **tool 级** | `PERMISSION_DENIED`，落 MCP 审计日志 |

L3 我们已经有了（`mcp_servers/registry.py`），只是目前跑在进程内。搬到 HTTP MCP Server 里，`caller` 从 Higress 透传的 consumer 身份取，**不信任请求体里的自称**。

### 3.3 这反而是升级

原来 `test_safety.py` 里那条「越权即拒绝」是单元测试。真机上它变成：

```
# 进 risk-analyst 的容器，直连征信 endpoint
kubectl exec -it worker-risk-analyst -- \
  curl -s -X POST $BUREAU_MCP_URL -d '{"method":"tools/call","params":{"name":"get_credit_report",...}}'
```

期望：**403**，且 Higress access log 与 MCP 审计日志**两侧同时留痕**。
这是评委能当场看的东西，比一行绿色的测试通过强得多。

## 5. 分阶段计划

时间盒按「两人并行、每天有效 6 小时」估。**T0 是硬伤修复，不做则现有交付物不可用；T1–T2 是最小可信真机；T3–T5 属复赛范围。**

### T0 — CR 合规化（0.5 天｜**建议 8.16 前必做**）

| # | 事项 | 完成判据 |
|---|---|---|
| T0-1 | `gen_agentteams.py` 支持 `--dialect upstream/annotated` | 生成 6 Worker + 1 Team + 1 Manager + 2 Human CR |
| T0-2 | `spec.model` 从 `config/models.yaml` 的 profile 解析出具体模型 ID | 每个 llm=true 的 Worker 都有非空 `model` |
| T0-3 | `soul` 内联、`env` 转 map、`mcp`→`mcpServers`、`skills` 拆 `remoteSkills` | —— |
| T0-4 | 离线 schema 校验：拿上游 CRD 的 openAPIV3Schema 直接校验我们的 CR | 新增 `tools/validate_cr.py`，进 `test_safety.py` |
| T0-5 | CRD 快照落库 `agentteams/upstream-crds/`，标注抓取日期与 commit | 防止上游漂移后无声失配 |

> T0-4 是关键：**不用集群也能验**。上游 CRD 就是一份 JSON Schema，本地校验一遍，`kubectl apply` 前就能知道会不会被拒。这条做完，「CR 可 apply」从口头承诺变成回归测试。

### T1 — 集群拉起（0.5–1 天）

```bash
# 前置：K8s 1.24+ / Helm 3.7+ / 默认 StorageClass
# 规格：6 Worker + Leader + Manager + 基础设施，实测建议 8C16G（官方 4C8G 是少量 Worker 的下限）
kind create cluster --name creditsentry

helm repo add higress.io https://higress.io/helm-charts && helm repo update
helm install agentteams higress.io/agentteams \
  -n agentteams-system --create-namespace \
  --set credentials.llmProvider=qwen \
  --set credentials.defaultModel=qwen3.5-plus \
  --set credentials.llmApiKey="$DASHSCOPE_API_KEY" \
  --set gateway.publicURL=http://localhost:18080
```

**三个必须注意的点**：

1. **Chart 的 `preflight.llm.strict=true`** —— 安装时会跑一次真实 LLM 探针，key 不通则 `helm install` 直接失败。先单独 curl 验一次 key，别在 helm 里排查网络问题。
2. **`credentials.llmApiKey` 是明文 values，Chart 不支持 `existingSecret`** —— 与我们「凭证只以引用形式出现」的不变量冲突。处理：只走 `--set` 从环境变量注入，**绝不生成含 key 的 values 文件进版本库**；装完立刻 `kubectl get secret` 确认 key 已落 Secret，并把该 Secret 名字记进部署文档。这一条要在 README 依赖披露里如实写明是**上游限制**，不是我们的设计。
3. 镜像源是阿里云杭州 ACR（`higress-registry.cn-hangzhou.cr.aliyuncs.com`），国内网络友好，不必配 Docker Hub 代理。

### T2 — MCP over HTTP + 权限下沉（1–1.5 天）

| # | 事项 | 说明 |
|---|---|---|
| T2-1 | 写 MCP Streamable HTTP 传输壳 | 4 个现有 Server 的 `TOOLS` 已经是标准 `inputSchema`，只需一层 JSON-RPC over POST。**继续用标准库，不引第三方依赖** |
| T2-2 | 新建 `sop-router` MCP Server | 复用 `routing.py` + `gate.py`，暴露 `next()` / `gate()` / `token()` 三个工具 |
| T2-3 | `caller` 身份改从 Higress 透传头取 | 不再信任请求体自称 |
| T2-4 | Higress 配 5 组 consumer 路由 + bureau/txn 两条出站脱敏规则 | 脱敏字段清单已在 `bureau_mcp.PII_FIELDS` |
| T2-5 | Worker CR 填 `mcpServers[].url` 指向网关 | —— |

### T3 — 可观测打通（0.5 天）

现状是 `trace.json` 落盘。两条路：

- **先试**：Chart 的 `cms.*` 段支持 OTLP 导出（`cms.endpoint` + `licenseKey`），但文档写的是阿里云 CMS 2.0/ARMS。**待验证 `cms.endpoint` 能否指向自建 OTel Collector**——能则零代码打通 Manager 与全部 Worker 的 Trace。
- **兜底**：写 `tools/trace_to_otlp.py`，把我们的 `trace.json` 转 OTLP/HTTP JSON 直投 Jaeger `:4318`。标准库 `urllib` 即可，不破坏零依赖承诺。

无论走哪条，验收点不变：Jaeger 里 `case → agent → skill → mcp → llm` 五层父子完整，且 `routing` / `adjudication` 两类自定义 Span 在。

### T4 — Skill 版本治理上真 Nacos（0.5 天）

上游 `remoteSkills.source` 要求 `nacos://host[:port]/namespace-id`，`authType` 三选一。
把 16 个 Skill 按 CreditSkill Spec 推上去，然后做一次**真实灰度回滚**：`RiskGate` v1.2.0 → v1.3.0 打标灰度 → 观察行为变化 → 回滚 → 行为复原。这是 Skill 那 25% 权重里「版本、发布、回滚」最直接的证据。

### T5 — 端到端与故障注入（1 天）

三条链路在真机重跑，加上 §6-B 的六项故障注入。

**合计 4–5 天**（不含缓冲）。

## 6. 验证方案

分三档。**核心原则：只列真机上才能验的项**——本地测试已覆盖的不重复列，否则部署白做。

### A. 真机独有验收（12 项）

| # | 验收项 | 怎么验 | 通过判据 |
|---|---|---|---|
| A-1 | CR 被 API Server 接受 | `kubectl apply -f agentteams/ --dry-run=server` | 8 个资源全部 accepted，零 warning |
| A-2 | Team 装配正确 | `kubectl get team credit-sentry` | `leaderReady=true`，`readyWorkers=6/6`，`phase=Active` |
| A-3 | **CR ↔ 权限矩阵零漂移（从集群读回）** | 从 API Server `kubectl get worker -o yaml` 导出，与 `permissions.py` 比对 | 完全一致。**注意与本地文件比对不同**：这一版验的是「集群里真实生效的」而非「仓库里写的」 |
| A-4 | **越权被拦（现场可复现）** | 进 `risk-analyst` 容器直连 `bureau-mcp` | HTTP 403 + Higress access log + MCP 审计日志**两侧都有记录** |
| A-5 | **工具级越权被拦** | `due-diligence` 调 `credit-core-mcp.adjust_limit`（同 server，非授权工具） | `PERMISSION_DENIED`。这条证明 §3 的 L3 层真在工作 |
| A-6 | PII 脱敏发生在网关 | 抓 `due-diligence` 收到的征信响应体 | `legal_rep_id_no` / `contact_phone` / `bank_account` 已掩码；对比 MCP Server 侧出站原文，确认脱敏点在网关**不在应用** |
| A-7 | 异构对抗真机成立 | `kubectl get worker risk-analyst devils-advocate -o jsonpath='{.items[*].spec.model}'` | 两者分属不同 family |
| A-8 | 密钥不落 CR、不落 Trace | `kubectl get worker,team,manager -o yaml \| grep -E 'sk-[A-Za-z0-9_-]{16,}\|AKIA[0-9A-Z]{16}'` | 无命中；Worker 容器 `env` 内无长期密钥 |
| A-9 | 一案一房间 + 人真的在里面 | Element Web 打开 case room | 6 个 Agent + 2 个 Human CR 账号在房；协作对话可读 |
| A-10 | **L2 审批是真人动作** | 风险经理账号在房间内回复审批 | 审批回调驱动执行；拒绝则 `→ NO_ACTION`。两条路径都跑 |
| A-11 | Trace 五层完整 | Jaeger UI | 父子关系正确，`routing` / `adjudication` 两类自定义 Span 在，`routing_key` / 规则 ID / 规则版本三字段齐全 |
| A-12 | Nacos 灰度与回滚 | `RiskGate` v1.2.0→v1.3.0→回滚 | 行为随版本变化并可完全复原；`kubectl` 不需要改任何 Worker CR |

### B. 故障注入（6 项）

真机的价值一半在这里——本地跑不出真实的超时和网络分区。

| # | 注入 | 期望行为 |
|---|---|---|
| B-1 | `bureau-mcp` 注入 3s 延迟 + 限流 429 | 按 Skill 声明的 failure policy 退避重试，超阈值转 `EVIDENCE_GAP` 而**不是**编造证据 |
| B-2 | `judicial-mcp` 直接下线 | 降级为「证据缺失」等级，结论不成立而非硬出结论 |
| B-3 | Nacos 不可达 | Worker 用本地缓存版本继续跑，并在 Trace 标记降级；**不静默使用未知版本** |
| B-4 | 审批超时 24h 无人响应 | 升级路径触发（Manager 拉更高权限人入房），不自动执行 |
| B-5 | `disposition-executor` 执行到一半 OOM 重启 | 幂等键生效，重放不产生第二次额度变更 |
| B-6 | **Team Leader 绕过 `sop-router` 直接指挥** | Worker 侧因无放行令牌拒绝执行并落合规事件（§2 的 B 方案兜底） |

B-6 是刻意设计的自证项：它验的是「我们的核心主张在被违反时会被发现」。

## 7. 风险与退路

| 风险 | 概率 | 退路 |
|---|---|---|
| 上游 CRD 在部署当天又变 | **高**（v1beta1 仍在演进） | T0-5 的 CRD 快照 + T0-4 的离线校验器，30 分钟内能定位失配字段 |
| Helm 安装受阻（镜像 / 资源 / preflight） | 中 | 先在 kind 上跑通再上云；preflight 失败先单独验 key |
| 8.16 前跑不完 | 中 | **降级到 §2 方案 C**：基础设施真机 + 业务闭环 PoC，并在 README 明确标注哪些截图来自真机、哪些来自本地。宁可标注清楚，不可含糊 |
| `cms.endpoint` 不能指向自建 Collector | 中 | T3 兜底方案（自写 OTLP 导出器），不阻塞 |
| Matrix 房间里 LLM 协作不稳定 | 中 | 这正是选 §2-B 的原因：流程由 `sop-router` 兜底，LLM 抖动不会让流程走错，只会让对话啰嗦 |

**优先级建议**：T0 在 8.16 前必做——现在提交的 CR 若被评委实际 apply 会当场失败，这是硬伤，且修复成本只有半天。T1–T2 尽力争取，T3–T5 归复赛。
