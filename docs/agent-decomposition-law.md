# Agent 拆分法则：Agent 边界 = 工具权限边界

> 信衡 CreditSentry 的方法论产出物，与具体业务解耦，可独立开源复用。

## 问题

多 Agent 系统设计中最没有答案的问题是：**到底该拆几个 Agent？**

常见做法是按业务步骤拆——有几个环节就有几个 Agent。这经不起追问：为什么不是把两个环节合并？为什么不再拆细一点？「因为流程是这样的」不是工程理由，只是对业务流程图的复述。

结果是两类失败：
- **拆太粗**：一个 Agent 同时持有取证工具和决策职责，产生确认偏差；执行者同时负责审计，无人制衡。
- **拆太细**：把一个取证职责拆成三个 Agent，它们做同样的事、有同样的权限，只是多了两跳消息和三倍 Token。

## 法则

> **Agent 边界 = 工具权限边界，不是业务步骤边界。**

**必须拆分**，当且仅当满足其一：
- **(i) 权限不可合并**：两个职责的工具权限集合并后会造成越权——即合并后的 Agent 能做到任一原职责都不该做的事。
- **(ii) 目标函数对立**：两个职责的优化目标相互矛盾，置于同一上下文会自洽坍缩（LLM 强烈倾向于让自己的前后输出保持一致，因此无法在同一上下文里真诚地自我反驳）。

**必须合并**：若两个职责的**权限集相同、目标函数一致、失败处理策略相同**——合并。否则只增加消息跳数与 Token，不增加任何控制力。

## 为什么这条法则成立

1. **权限是唯一可静态验证的边界。** 职责描述是自然语言，会漂移；权限是配置，可 diff、可审计、可在 CI 里断言。把 Agent 边界锚定在权限上，架构就从「文档承诺」变成「可执行约束」。
2. **它让 Agent 数量可推导、可证伪。** 给定工具清单，权限等价类的数量是算出来的，不是拍的。任何人都可以用「合并这两个会越权吗？」和「拆开这两个有增益吗？」来检验。
3. **它天然对齐既有的组织内控制度。** 企业的职责分离制度本质上就是权限划分。按权限拆 Agent，等价于把制度编译成拓扑——**内控即拓扑**。

## 应用示例（CreditSentry）

给定 4 个 MCP 数据源、1 个写触点、1 个证据账本、1 个知识库，按权限等价类聚类得到 5 类：

| 权限等价类 | Agent |
|---|---|
| 内部只读聚合 | SignalHub |
| 唯一外部 PII 取证触点 | DueDiligence |
| 零工具纯推理 | Analyst 类 |
| 唯一写触点 | DispositionExecutor |
| 唯一 Trace 读 + 知识库写 | ComplianceAuditor |

再由判据 (ii) 把「Analyst 类」拆为 `RiskAnalyst`（求证风险成立）与 `DevilsAdvocate`（求证风险不成立）——两者权限集**完全相同**，但目标函数对立。

**结论：6 = 5 个权限等价类 + 1 个目标函数对立拆分。**

### 反向检验

**为什么不是 4？** 合并即越权，逐条可证：
- `DueDiligence + RiskAnalyst` → 定性者持有取证工具，边查边下结论产生确认偏差；且 PII 触点从 1 个扩散到 2 个，出站脱敏范围失控。
- `RiskAnalyst + DevilsAdvocate` → 同一上下文自我质疑，对抗性坍缩，质疑沦为走过场。
- `DispositionExecutor + ComplianceAuditor` → 执行者自审，直接违反不相容职务分离。

**为什么不是 10？** 若把 `DueDiligence` 拆成征信官／司法官／流水官：三者共享同一权限集（外部只读 + 写证据账本）、同一目标函数（摆事实不下结论）、同一失败处理策略（重试后降级标注）。按合并判据必须合并。拆分只增跳数与 Token，不增控制力。

## 适用边界

- 该法则解决**「拆几个」**，不解决**「怎么编排」**——后者由 SOP 状态机路由承担。
- 在没有副作用、没有敏感数据、没有合规要求的场景（如纯创意生成），权限维度退化，此法则给出的答案会趋近于 1，此时应改用其他判据（如上下文长度、专业领域差异）。
- 判据 (ii) 依赖「同上下文会自洽坍缩」这一经验观察。若未来模型具备稳定的上下文内自我对抗能力，该判据可能失效，届时 6 应退化为 5。**这是本法则可被证伪的地方，我们明确标注而非回避。**
