# 风险处置工作台 · 使用说明

> 一个抽象的 Agent 架构，评委无法通过读代码在 8 分钟内建立信任。
> 这个工作台把它放回**真实业务场景**：银行贷后风险经理的一天。

```bash
python3 poc/serve.py --open        # 起服务并自动打开浏览器
```

零依赖、零配置、不联网（默认 stub 模式）。浏览器打开 ``。http://127.0.0.1:8090/

---

## 一、场景设定

> 早上 9 点，风险经理打开工作台。预警池里进来三笔案件。
> 他点开一笔，系统自动完成取证、定性与质疑，**在需要他拍板的地方停下来等他**。
> 他批准或驳回，系统执行并出具处置意见书与审计报告。

界面按这个流程组织成三栏：

| 栏位 | 内容 | 回答的问题 |
|---|---|---|
| **左** | 预警池 · 运行设置 · 因子调节 | 我要处置哪一笔？用什么模型？ |
| **中** | 五阶段流水线 + 处置过程卡片流 | 系统做了什么，结论是什么，为什么 |
| **右** | 决策链路 / 运行日志 / MCP 审计 / Agent 编制 | 这一切是怎么发生的，能不能查 |

## 二、七个演示动作

每一个都对应一条设计主张。**建议按顺序做，8 分钟能走完前四个。**

### ① 抓住真风险，且结论可点开验证

选 `CASE-001` → 审批方式保持「停下来问我」→ **开始处置**。

看点：
- 五阶段流水线逐段点亮；右栏决策链路实时滚动
- 「证据账本」卡片里**点任意一行**，弹出该证据的原文快照 URI、sha256 哈希、定级理由与抽取字段
- 处置意见书正文里的 `[EV-xxxx-xxxx]` 角标**可以点**

> 一句话：**结论不是模型说的，是证据链推出来的。**
> 证据原文绝不进入模型上下文——模型看到的是抽取字段，原文靠哈希锚定。

### ② 对抗质疑：让 Agent 敢说「这不是风险」

同一次运行，看「定性 ⇄ 对抗质疑」卡片。左右两栏并排，每条主因下面直接跟着质疑官的结论。

看点：
- 两侧标注的**模型族不同**（qwen ⇄ deepseek）。拆成两个 Agent 是为了避免自洽坍缩；
  若共用同一批权重，坍缩只是从上下文层面搬到权重层面——**配成同族会被拒绝启动**
- 「质疑清单覆盖 100%」：清单由系统从定性方断言派生，**不由模型自报**，返回后逐项核对

再跑 `CASE-002`：**同一类主体、完全相同的三类信号，结论相反**。

> 一句话：**让 Agent 敢说「这不是风险」，比让它报警难得多。**
> 误杀正常客户会直接抽贷断贷、引发投诉与监管问责。

### ③ 审批闸门：它真的会停下来

`CASE-001` 跑到处置阶段，页面顶部弹出橙色横幅「案件已暂停，等待人工审批」，
中栏出现审批操作卡。**此时后端线程真的阻塞在那里等你点击**——不是动画。

点 **驳回**，然后看：
- 处置层级从 `L2` **降级为 `L0`**
- 「执行回执」卡片不再出现
- 右栏「MCP 审计」里**没有任何 `adjust_limit` 成功记录**——额度确实没被改

> 一句话：**审批被拒即降级为只读，这是代码保证的，不是承诺。**

### ④ 结论由证据驱动，不是硬编码

左栏「因子调节」把三个因子都切到第二档：

| 因子 | 切换为 | 预期 |
|---|---|---|
| 涉诉实质性 | 已结案 · 我方原告 · 占比 <5% | 质疑方推翻「偿债能力恶化」 |
| 资金对手方性质 | 历史稳定供应商且落在波动区间内 | 质疑方推翻「资金用途异常」 |
| 法代变更时点 | 早于风险窗口且股权未变动 | 质疑方推翻「实际控制人风险」 |

重跑 → 裁决从 `RISK_CONFIRMED` 翻为 **`RISK_REFUTED`**，层级降到 `L0`。

**只切一个因子**也值得演示：对应主因被推翻，但风险整体仍成立（还有另两条主因），
层级不变。这说明系统既不因单点动摇，也没有对因子视而不见。

> 可改字段是白名单里被逐条说清楚的那几个（`mcp_servers/world.py` 的 `FACTORS`），
> 每个都绑定一条业务口径。递给评委的是一张**可改字段卡片**，既开放又有边界。
>
> 这条性质由 `poc/test_safety.py` 断言：**因子翻转后质疑结论必须随之翻转**，
> 做不到就说明结论其实是硬编码的。

### ⑤ 四维闸门真的在分级

因子调节里把**敞口金额**切到「2 亿（大型集团客户）」，其余不动，重跑。

同一个「压降 30%」动作，620 万时是 `L2`（审批后执行），2 亿时升为 **`L3`（只出方案，系统不执行）**。
闸门卡片上四个维度（风险等级 × 证据等级 × 敞口 × 可逆性）与命中的规则号都写着。

也可以直接跑 `CASE-003`——2017 年山东某担保圈风险传染案的**真实历史回溯**，
时点冻结在 `2017-04-01`。案件闭环后才揭晓历史结局：**31 个月后债券违约**。
该结局在数据构造时就被摘出，Agent 全程取不到，是结构约束而非约定。

### ⑥ 越权调用会被挡，而且留痕

右栏切到「MCP 审计」→ 点 **发起越权调用**。
让**零工具权限**的风险定性官去调信贷核心的写接口 → `PERMISSION_DENIED`。

看点：审计日志里出现一条**红底的被拒记录**。

> 一句话：重点不是它被拒了，而是**被拒的调用也会出现在审计日志里**。
> 一个只在成功路径留痕的系统，没法向监管解释「有没有人试过绕过去」。

### ⑦ 转人工也是一次有交付物的收尾

系统并不是「跑不通就算了」。当自动取证与裁决收敛不了时，它的**最后一个动作**
是把工作交接清楚，而不是把问题原样丢给人。

怎么现场演示这条路径：

```bash
python3 tools/mock_llm_server.py --fault always-bad --port 8077   # 另开终端
```

工作台里判断方式选 **接入大模型**、模型方案选 `offline-mock`，跑 `CASE-001`。
模型持续给不出合规输出 → 定性与质疑双双降级 → 回退用尽 → 转人工。

界面上会出现**转人工交接单**卡片，落盘产出《取证任务清单.md》，内容包括：

| 章节 | 回答什么 |
|---|---|
| 移交原因 | **取自实际发生的事**：材料确实不够？还是推理环节失效？两者要人做的事完全不同 |
| 一、为什么停在这里 | 回退了几轮、每轮为什么、完整阶段轨迹 |
| 二、已经查到了什么 | 已取得材料清单，**接手的人不必重复劳动** |
| 三、还缺什么，找谁补 | 每项标注：去哪个系统取、要什么授权、**哪个岗位负责**、建议动作 |
| 四、补齐之后怎么办 | 回流条件，以及「不得引用本单作为风险结论」 |
| 五、合规留痕 | 「我们看过、没能定论」这个过程本身也要可举证 |

三个看点：

- **交接单不给风险结论。** 抬头就写着「系统未对本案作出任何风险结论」——
  证据不足以定论时给结论就是编。它给的是工作交接，不是判断。
- **待补项区分「系统能重取的」与「只能靠人要的」。** 财务报表不在任何可查系统内，
  系统重试多少次都拿不到，只能由客户经理向客户索取——**这正是转人工存在的理由**。
- **本次没产出的旧报告会被清掉。** 一个声明「未作出结论」的案件，
  目录里却躺着上一次运行的《处置意见书》，会直接打脸。这条由回归断言守着。

## 三、接你自己的模型 API

左栏「推理后端」切到 **live**，下面会出现**模型凭证**面板。两条路：

### (a) 只用一个平台 —— 推荐先试这条

模型方案选 **`single · 只用一个平台`**，然后：

1. 从下拉里选平台（百炼分**国际站**与**中国大陆**两个，别选错）
2. 填一个 API Key
3. 点 **检测可用模型**

系统会用十几个候选模型逐个探你的账号，然后直接告诉你结论：

```
检测到 7 个可用模型，分属 2 条技术路线。
  qwen       qwen-max、qwen-plus、qwen-turbo
  deepseek   deepseek-v3、deepseek-r1

建议这样分工，一个 Key 就够：
  风险定性岗　qwen-max（qwen）
  对抗质疑岗　deepseek-v3（deepseek）      [ 就按这个配置 ]
```

点「就按这个配置」即可，两个岗位指向同一个平台、不同模型。

> **一个平台够不够，取决于它上面挂了几条技术路线，而不是几家厂商。**
> 百炼上同时挂着通义千问与 DeepSeek，所以一个 Key 就能满足「两边不同源」。

**只检测到一条路线怎么办**（比如账号里只开通了 qwen）：

- 去该平台的「模型广场」再开通一个别家的模型——百炼上就有 DeepSeek 系列，
  开通后回来重新检测即可；
- 或者换用需要两个 Key 的方案，或装个本地 Ollama 补第二条路线。

系统不会因为「只有一个平台」就放宽这条约束：两边同源时，
负责唱反调的那个岗位其实是在自说自话，这时候的「质疑通过」没有意义。

### (b) 用预置的服务商

选一个预设，面板会列出需要哪几个 Key、**谁在用**、模型名与端点，以及**去哪儿申请**。
已经 `export` 过的会显示「来自环境变量」。

| 预设 | 定性 ⇄ 质疑 | 需要什么 |
|---|---|---|
| `dashscope-only` | qwen-max ⇄ deepseek-v3 | 百炼**国内站** 1 个 Key |
| `dashscope-intl-deepseek` | qwen-max（百炼国际站）⇄ deepseek-chat | 百炼**国际站** + DeepSeek 各 1 个 Key |
| `dashscope-intl-ollama` | qwen-max（百炼国际站）⇄ llama3.1 | 百炼国际站 1 个 Key + 本地 Ollama |
| `deepseek-zhipu` | deepseek-chat ⇄ glm-4-plus | DeepSeek + 智谱各 1 个 Key |
| `local-ollama` | qwen2.5 ⇄ llama3.1 | 全本地，零 Key |

> **百炼有两个互不相通的地域端点，Key 不能跨地域用。** 拿国际站（新加坡）的 Key 打
> 中国大陆端点，返回的是 `401 Incorrect API key`——看起来像 Key 抄错了，实际是地域不匹配。
> 这是接入时最容易卡住的一个坑，所以先确认你的账号注册在哪一边：
>
> - 控制台域名是 `bailian.console.aliyun.com` → 国内站，用 `dashscope-only`
> - 控制台域名是 `bailian.console.alibabacloud.com` → 国际站，用 `dashscope-intl-*`
>
> 另外国际站默认通常**只开通 qwen 系列**，deepseek / llama / glm 会返回 404。
> 单靠 qwen 凑不出两个模型族，所以国际站的两个预设都要再配一个别族的来源。

### (c) 自定义端点 —— 两个平台分别指定时用这个

模型预设选 **`custom · 自定义端点`**，为两个角色分别填：

| 字段 | 说明 | 例 |
|---|---|---|
| `base_url` | **写到 `/v1` 这一层**，系统自己接 `/chat/completions` | `https://api.deepseek.com/v1` |
| 模型名 | 与服务商控制台里完全一致 | `deepseek-chat` |
| 模型族 | 留空自动从模型名推断，可手动改 | `deepseek` |
| 数据驻留区 | 境内 / 本地 / 境外 | 境内 |
| API Key | 只进本进程内存 | — |

> **只给 API Key 是不够的。** `base_url` 决定请求发到哪里——端点对不上，
> Key 填得再对也调不通。这是接入失败最常见的原因。

两条约束对自定义端点**同样生效**，不因为「是你自己填的」就放行：

- **两侧模型族必须不同**。配成同族会被拒绝启动——拆成两个 Agent 是为了避免自洽坍缩，
  同族权重会让对抗从上下文层面坍缩到权重层面。
- 数据驻留区选「境外」时，唯一 PII 触点会被 **PII 围栏**拦下。这是设计如此。

### 填完点「保存并测试连接」

会对每个端点发一次几十 token 的探针，当场给结论：

```
✓ dashscope/qwen-max        812 ms   连通且已鉴权，返回 {"ok": true}
✗ custom-devils-advocate/xxx         HTTP 404　端点或模型名不存在，核对 base_url 与 model
```

401 / 403 / 404 / 429 都翻译成人话，不用去猜。**先测通再跑案件**——
不然会在链路中途失败，排查成本高得多。

### 凭证的存放

**只存在本进程内存**：不写文件、不进配置、不进 Trace 与日志，重启服务即失效；
接口只返回名字与来源，从不回显值。这条由 `poc/test_safety.py` 断言——
跑完整条链路后在 Trace / 日志 / 审计 / 账本里搜哨兵值必须搜不到。

> 改变的只是「到哪里取值」，不是「配置里能不能写明文」。
> `config/providers.yaml` 里写的仍然是 `env:DASHSCOPE_API_KEY` 这样的**引用**。

也可以完全走命令行，启动服务前 `export` 环境变量，效果相同：

```bash
export DASHSCOPE_API_KEY=...
python3 tools/preflight.py --preset dashscope-only    # 与界面上「测试连接」同一套判断
python3 poc/serve.py --open
```

live 模式下顶栏的 **Token / 成本**会显示真实用量；若模型输出不合规触发了修复轮，
或触发了失败策略降级，会在运行日志里以 `WARN` / `ERROR` 显式打出来——**降级必须留痕**。
详见 [真机部署与 API 方案](真机部署与API方案.md)。

## 四、它和命令行是什么关系

**同一套代码，同一份产出。** 工作台没有另造一条链路：

| | 命令行 | 工作台 |
|---|---|---|
| 编排 | `Orchestrator.run()` | 同一个 |
| 审批 | `--deny-approval` 开关 | 同一个 `approval_handler`，只是阻塞等浏览器点击 |
| Trace | 跑完落 `trace.json` | 同一份数据，通过观察者实时推送 |
| 产出 | `poc/out/<case>/` 九个文件 | **完全相同**，工作台跑完照样落盘 |

工作台加的只有三个**旁路**钩子（Span 观察者、日志出口、审批回调），
且它们抛错一律吞掉——**可视化坏了不能反过来弄坏业务链路**。
这条方向性由 `poc/test_safety.py` 断言：观察者故意抛异常时，业务结果必须逐字段不变。

## 五、接口一览

工作台后端是 REST + SSE，前端可以整个替换掉。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/bootstrap` | 案件、因子、预设、Agent 编制、权限矩阵、动作白名单、路由表 |
| POST | `/api/runs` | `{case, llm_mode, preset, approval_mode, factors}` → `{run_id}` |
| GET | `/api/runs/<id>/stream?from=<seq>` | **SSE**：`run_started` / `span_start` / `span_end` / `log` / `phase` / `approval_required` / `done` / `error`。断线带 `from` 续传 |
| GET | `/api/runs/<id>` | 终态快照 |
| POST | `/api/runs/<id>/approve` | `{approved, approver, reason}`，解除阻塞 |
| POST | `/api/runs/<id>/probe` | 越权调用演示，返回被拒结果与新增审计条目 |
| GET | `/api/runs/<id>/report/{opinion\|audit}` | 成文报告的 markdown |

事件是 **append-only 的序列**而不是可变状态：浏览器带着已收到的 `seq` 订阅，
断线重连从断点续传。与证据账本 append-only 是同一个理由——**可回放的前提是没人能偷偷改历史**。

## 六、边界

- 单机演示服务，**未做鉴权、多租户与并发隔离**，不要暴露到公网
- 运行实例存在内存里，进程重启即丢失（产出文件仍在 `poc/out/`）
- 4 个 MCP Server 仍为 Mock；Tool 名称与 Schema 已按与真实系统零差异设计
- 界面在 1180px 以下会退化为单列，能用但信息密度下降；演示建议用 ≥1400px 的屏幕
