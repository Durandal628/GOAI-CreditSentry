# 核心 Skill 清单

> 对应参赛说明 **附录 B**，并在其 10 个字段基础上增加两个金融特色字段：**绑定监管条款**、**回归评估集**。
> 项目：信衡 CreditSentry。共 16 个核心 Skill。

---

## 分层原则：领域判断力自研，通用云操作复用官方

我们不重复造基础能力的轮子——这正是赛题第 10 章对云 Skills 的定位（「不再需要额外构建一些基础能力的 Skill」）。

| 层 | 内容 | 数量 | 归属 |
|---|---|:--:|---|
| **L3 领域判断层** | 信贷风控领域知识、监管条款绑定、证据语义 | 12 | 全自研（核心资产 / 开源贡献物） |
| **L2 领域封装层** | 自研外壳 + 编排官方能力，两层的接缝 | 4 | 自研封装 |
| **L1 云操作层** | 对象存储、向量库、日志检索、云监控、消息通知、RAM 鉴权 | — | **直接调用官方用云 Skills，不自研** |

### 可替换性（无厂商锁定）

| 官方能力 | 开源等价替代 | 迁移成本 |
|---|---|---|
| 对象存储 OSS | MinIO | 仅换 endpoint 与凭证，S3 协议兼容 |
| 日志服务 SLS | Loki | 查询语法适配层约 1 个文件 |
| 向量检索 DashVector | pgvector | 共用 L2 `VectorStore` 接口 |
| 云监控 CMS | Prometheus | OTel Exporter 直接切换 |

**PoC 默认走开源替代**（本地 docker-compose 可完整跑通），生产接入切官方 Skill——两者共用同一套 L2 接口契约，**切换不改调用链**。

## CreditSkill Spec —— Skill 规范（本身即开源贡献物）

每个 Skill 目录统一三件套：

```
skills/<skill_name>/
├── SKILL.md        # 本清单的全部字段
├── schema.json     # 输入 / 输出 JSON Schema（运行时强校验）
└── eval/           # 回归评估集：版本升级必须全绿才可发布
    ├── cases.jsonl
    └── expected.jsonl
```

目录与元数据格式对齐 skills.sh / Nacos Skill Registry，保证可分发。
**版本治理**：Nacos 标签灰度发布 → 运行时按标签加载 → 调用审计回传版本号 → 异常一键回滚。监管口径变化只需升 Skill 版本，**不改 Agent 代码**。

# L3 领域判断层（12 个 · 全自研）

## 1. SignalFusion

| 字段 | 内容 |
|---|---|
| **类型** | 自定义 Skill（诊断类） |
| **使用场景** | INTAKE 阶段，把多源零散预警信号归并为可处置的风险事件 |
| **输入参数** | `signals[]{source, subject_id, signal_type, ts, payload}`、`window`（归并时间窗）、`dedup_policy` |
| **输出结果** | `RiskEvent{event_id, subject, signal_types[], first_seen, priority, dropped[]{signal_id, reason}}` |
| **调用条件** | 预警池新增信号，或定时批量归并触发 |
| **依赖工具 / 系统** | 内部预警池（读）；无外部依赖 |
| **失败处理** | 单源不可用 → 降级为可用源归并并在输出标注 `degraded_sources`；全源失败 → 抛错升级人工，**不产出空事件** |
| **权限与安全** | 只读，无 PII；仅 SignalHub 可调用 |
| **绑定监管条款** | 《商业银行贷后管理指引》风险监测与预警要求 |
| **回归评估集** | 30 组信号流样例，校验降噪率与**零高危漏丢**（被丢弃信号必须可回溯） |
| **复用价值** | 场景无关的信号归并内核，可直接复用于保险报案归并、告警降噪、工单去重 |

## 3. RiskRootCause

| 字段 | 内容 |
|---|---|
| **类型** | 自定义 Skill（诊断类） |
| **使用场景** | ADJUDICATION 阶段，基于已登记证据做风险归因与分类建议 |
| **输入参数** | `evidence_ids[]`、`exposure`、`policy_context`（RAG 召回）、`historical_cases[]` |
| **输出结果** | `RiskAssertion{root_causes[]{type, confidence, evidence_ids[]}, suggested_grade, evidence_gaps[]}` |
| **调用条件** | EVIDENCE 阶段完成且 `evidence_sufficiency ≥ 0.7` |
| **依赖工具 / 系统** | LLM 推理；`PolicyRag`、`CaseMemory` 提供上下文 |
| **失败处理** | 证据不足 → **强制**输出 `evidence_gaps` 并将结论置为 `INSUFFICIENT`，Case 回退 EVIDENCE；LLM 超时 → 重试 2 次后升级人工 |
| **权限与安全** | **零工具权限**（刻意剥夺，防边查边下结论的确认偏差）；Schema 拒绝无 evidence_ids 的断言 |
| **绑定监管条款** | 《贷款风险分类指导原则》五级分类标准 |
| **回归评估集** | 40 组已标注案例（含 10 组误报陷阱），校验分类准确率与**无证据结论率 = 0** |
| **复用价值** | 「证据 → 归因 → 分级」范式可复用于保险核赔定性、故障根因定位 |

## 7. GuaranteeProbe

| 字段 | 内容 |
|---|---|
| **类型** | 自定义 Skill（取证类） |
| **使用场景** | EVIDENCE 阶段，把「对外担保」从台账上的一个静态数字变成一笔可判定的或有敞口 |
| **输入参数** | `subject_id`、`direct_exposure`（用于计算净敞口相对倍数） |
| **输出结果** | `GuaranteeFacts{担保余额, 已出险被担保方[], 缓释措施[], 覆盖率, 净未覆盖敞口, 相对直接敞口倍数}` + `evidence_ids[]` |
| **调用条件** | 取证任务含 `guarantee_contagion` 类型，或敞口测绘发现已出险关联主体 |
| **依赖工具 / 系统** | `credit-core-mcp`（只读） |
| **失败处理** | 台账为空 → 登记为**有效负向证据**而非取证失败（「查了没有」与「查不到」是两种证据状态）；被担保方状态无公开定论 → 标注 `ambiguous` 降为弱证据，**不自动认定出险** |
| **权限与安全** | 只读；担保关系与金额属敏感数据，出站脱敏 |
| **绑定监管条款** | 《商业银行大额风险暴露管理办法》关联客户与担保链认定；《商业银行贷后管理指引》或有负债监测 |
| **回归评估集** | 10 组担保结构样例，**含 3 组「缓释措施已全额覆盖，不构成风险」的误报陷阱**，另含缓释超额申报的边界 |
| **复用价值** | 「或有负债 → 净敞口」的测算范式可复用于供应链金融确权、融资担保机构代偿测算 |

> **两条口径值得单独说明。**
> 一是**「圈子大」不是风险，「圈里有人出事」才是**——被担保方未出险时，担保余额再大也不计入代偿敞口。
> 二是**或有负债的置信度必须低于已实现风险**：代偿要求被担保方真的违约、债权人真的主张、
> 缓释真的不足，三件事同时成立才转化为本行损失。因此定级只看净未覆盖敞口相对直接敞口的倍数，
> 且置信度上限为 0.75——低于「次级」的 0.85 门槛，即**或有代偿单独不足以把客户定到次级**。

## 8. QueryRewrite

| 字段 | 内容 |
|---|---|
| **类型** | 自定义 Skill（知识类） |
| **使用场景** | 任何检索政策或历史案例的环节，**检索前必调** |
| **输入参数** | `base_query`、`stance`（PROVE / REFUTE）、`signal_types[]`、`facts`、`as_of` |
| **输出结果** | `QueryPlan{subqueries[]{dimension, text, filters, why, weight}, clarifications[]}` |
| **调用条件** | RiskAnalyst / DevilsAdvocate / ComplianceAuditor 检索前 |
| **依赖工具 / 系统** | 自研术语表与信号主题映射，**纯函数无外部依赖** |
| **失败处理** | 未知立场 → 直接抛错不猜；术语表未覆盖 → 降级为仅立场维与信号主题维，并在 Span 标注 `dimensions_used` 以便事后补词表 |
| **权限与安全** | 只读纯函数；不接触任何业务数据 |
| **绑定监管条款** | 《商业银行贷后管理指引》条款适用性判断——条款须在案件时点已生效 |
| **回归评估集** | 18 组，覆盖六维各自的**触发与不触发**条件（如求证方不得产生否定式子查询），以及澄清三渠道的选路正确性 |
| **复用价值** | 立场维 + 否定式维的组合是对抗式检索的通用范式，可复用于合同审查、尽调抗辩、审计发现的反向验证 |

### 六个维度

| 维 | 解决什么 |
|---|---|
| `stance` 立场 | 求证方找**构成要件与认定标准**，证伪方找**认定门槛**。对抗式设计在检索层的延伸 |
| `terminology` 术语规范化 | 行内口语 → 监管术语（抽贷→提前收回贷款、担保圈→关联客户认定）。不做这一维，业务口语几乎检不到条款原文 |
| `signal_topic` 信号主题 | 信号类型 → 绑定的条款主题，让检索由**案件事实**驱动而非只由角色固定查询词驱动 |
| `clause_ref` 条款直查 | 事实中出现条款号时**精确召回**——语义检索在「第十八条」这类精确引用上表现很差 |
| `negation` 否定式 | **仅证伪方**：主动检索「不构成 / 除外 / 豁免 / 不适用」。正向检索天然覆盖不到除外条款 |
| `recency` 时效 | **生效日 ≤ 案件时点** |

> **时效维修复了一个真实缺陷。** 跑真实回溯案例时发现，`as_of` 为 2017-04-01 的案件
> 召回了 2025-06-01 才生效的行内制度——这是**知识维度的前视污染**，与把后来才披露的
> 证据放进决策时点是同一类错误，只是更隐蔽，因为条款看起来「一直都在」。

### 澄清的三条渠道

需要补充信息时**不默认追问用户**。银行场景里补充信息的成本不在用户打字，
而在于「去哪个系统查、有没有查询授权」，所以澄清的产物应当是**可派发的任务单**。

| 渠道 | 何时用 | 例子 |
|---|---|---|
| `AUTO` | 已有明确规则可自动决定 | 流水采样不足 → 降为弱证据，不打扰任何人 |
| `SYSTEM_TASK` | 需去某系统查，人也答不上来 | 主体重名 → 派工商精确查询任务 |
| `HUMAN_CHOICE` | 确实需要人的**业务判断** | 被担保方是否已实质出险 → 房间内**选项式**提问并阻断 |

第三条必须给选项，不问开放问题——开放问题的回答无法结构化，也无法进证据账本。
该约束由回归断言强制。

## 9. RiskGate

| 字段 | 内容 |
|---|---|
| **类型** | 自定义 Skill（治理类）· **安全核心** |
| **使用场景** | DISPOSITION 阶段，计算处置动作的执行层级 L0–L3 |
| **输入参数** | `risk_grade`、`evidence_level`（强/弱/缺失）、`exposure_amount`、`action_type`、`reversibility` |
| **输出结果** | `Gate{action_tier: L0\|L1\|L2\|L3, 需审批: bool, 审批角色[], idempotency_key, rollback_point, 判定理由}` |
| **调用条件** | 裁决完成、进入 DISPOSITION 阶段时**强制**调用，无旁路 |
| **依赖工具 / 系统** | 纯规则引擎，无外部依赖（刻意设计：安全判定不依赖网络与 LLM） |
| **失败处理** | 任何入参缺失或规则未命中 → **默认降级为 L3**（只出方案不执行）。fail-safe 而非 fail-open |
| **权限与安全** | 规则表经 Nacos 版本管控，变更需双人审核；判定结果写审计日志 |
| **绑定监管条款** | 《商业银行内部控制指引》授权审批与不相容职务分离 |
| **回归评估集** | 全组合边界用例（含缺失入参、极端金额、未知动作类型），**校验不可逆动作永不落入 L0/L1** |
| **复用价值** | 四维闸门模型（风险 × 证据 × 金额 × 可逆性）是**场景无关的高风险动作管控内核**，可直接复用于运维自愈、保险赔付、自动化交易 |

| **类型** | 自定义 Skill（执行类）· **唯一写触点** |
| **使用场景** | DISPOSITION 阶段，幂等执行已裁决且已审批的处置动作 |
| **输入参数** | `DispositionOrder{action, params, action_tier, idempotency_key, rollback_point, approval_token}` |

| **复用价值** | 幂等 + 回滚点 + 审批验签的执行封装，是**任何有副作用 Agent 的通用安全底座** |

## 12. PostmortemDistill

| 字段 | 内容 |

| **类型** | 自定义 Skill（执行类） |

# L2 领域封装层（4 个 · 自研外壳 + 编排官方能力）

## 13. EvidenceLedger

| 字段 | 内容 |
|---|---|
| **类型** | 自定义 Skill（取证类）· **自研 + 官方复用的接缝** |
| **使用场景** | 全流程，登记证据并评定证据等级 |
| **输入参数** | `source_system`、`raw_content`、`extracted_fields`、`collected_at`、`subject_id` |
| **输出结果** | `Evidence{evidence_id, snapshot_uri, content_hash, level: 强\|弱\|缺失, 定级理由}` |
| **调用条件** | 任何外部原文被取回时**强制**调用——不经账本的数据不得进入决策 |
| **依赖工具 / 系统** | **自研**：证据等级评分、哈希存证语义、引用约束校验。**复用官方**：对象存储（快照）+ 数据库写入 |
| **失败处理** | 存储不可用 → 本地暂存队列 + 后台补偿；哈希冲突 → 拒绝写入并告警 |
| **权限与安全** | 仅 DueDiligence 可写；账本 append-only 不可篡改；快照加密存储 |
| **绑定监管条款** | 《商业银行内部控制指引》记录留存与可追溯要求 |
| **回归评估集** | 定级规则全覆盖 + 幂等写入 + 哈希校验，共 14 组 |
| **复用价值** | **证据账本是本项目最通用的开源组件**，任何需要「结论可举证」的 Agent 系统均可直接接入 |

## 14. PolicyRag

| 字段 | 内容 |
|---|---|
| **类型** | 自定义 Skill（知识类） |
| **使用场景** | ADJUDICATION 阶段，召回信贷政策、监管规则与行内制度 |
| **输入参数** | `query`、`top_k`、`filters{条款生效日期, 适用产品线}` |

| **调用条件** | RiskAnalyst / DevilsAdvocate 需要政策依据时 |
| **依赖工具 / 系统** | **自研**：政策切分策略、条款对齐、召回后证据化。**复用官方**：向量库建库与相似度检索 |

| **绑定监管条款** | —（本 Skill 是条款的检索侧） |

| **复用价值** | 「召回即证据化」（每条召回自动登记 evidence_id）的做法可复用于所有合规类 RAG |

## 16. ReportCompose

|---|---|

## Skill 与多 Agent 协同流程的关系

| 阶段 | 主责 Agent | 调用的 Skill |
|---|---|---|
| INTAKE | SignalHub | `SignalFusion` → `ExposureMapping` |
| EVIDENCE | DueDiligence | `CreditReportProbe` / `LitigationProbe` / `TxnFlowAnalyze` / `GuaranteeProbe` → 每条产出经 `EvidenceLedger` 登记 |
| ADJUDICATION | RiskAnalyst ⇄ DevilsAdvocate | 双方各自调用 `PolicyRag`、`CaseMemory`；RiskAnalyst 另调 `RiskRootCause` |
| DISPOSITION | RiskCommander → Executor | `RiskGate`（定级）→ `ReportCompose`（意见书）→ `SafeDisposition`（执行） |
| AUDIT | ComplianceAuditor | `ComplianceCheck` → `ReportCompose`（审计报告）→ `PostmortemDistill`（回流） |
