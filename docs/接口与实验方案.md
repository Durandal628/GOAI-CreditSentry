# 一、LLM 接口方案

## 1.1 现状与缺口

现有契约极简，只有一个方法：

```python
complete_json(task: str, system: str, payload: dict) -> tuple[dict, int, int]
```

两个实现（`StubLLM` / `OpenAICompatLLM`），两个调用点（`risk_root_cause` / `devils_advocate`）。

**已经做对的部分**，不要在重构时丢掉：任务是**带类型的**（`task` 而非自由对话）；输入输出都是 JSON；返回值自带 token 计数；Span 属性对齐 OTel GenAI 语义；**LLM 的暴露面被刻意压到只有两处**——这是「LLM 只做阶段内判定」的物理保证。

**七个缺口**（前两个已修复，见 §1.2）：

| # | 缺口 | 后果 | 状态 |
|---|---|---|---|
| 1 | **无模型路由**：三个进程级环境变量指定唯一端点，所有 Agent 共用 | 同一进程内无法让不同 Agent 用不同模型——异构对抗根本无法落地；也无法回答「哪些数据发给了哪个厂商」 | **已修复** |
| 2 | PII 出站脱敏无代码强制点 | 设计上说 Higress 兜底，代码里没有断言 | **已修复**（数据驻留围栏） |
| 3 | 无输出 Schema 校验 | live 模式模型返回不合规 JSON 时直接崩到下游 | 待做 |
| 4 | prompt 硬编码在函数体里 | 改口径 = 改代码；Trace 里没有 `prompt_version` | 待做 |
| 5 | 失败策略只写在 `SKILL.md`，没有执行点 | 「重试 2 次后升级人工」目前是文档承诺 | 待做 |
| 6 | 无成本与时延预算 | 单案件开销无上限 | 部分（已记账未设限） |
| 7 | stub 与 live 之间是断崖 | 要么可复现但不是真模型，要么是真模型但不可复现 | 待做 |

## 1.2 模型配置的四层分离【已实现】

缺口 1 与 2 的修法不是「加一个模型参数」，而是把配置拆成四层。

| 层 | 位置 | 回答什么 |
|---|---|---|
| 1 · Provider 注册表 | `config/providers.yaml` | 端点在哪、什么协议、**凭证怎么取**、数据落在哪个驻留区 |
| 2 · 模型档位 | `config/models.yaml` | 用哪个模型、怎么解码、多少钱、属于哪个 `family` |
| 3 · Agent 绑定 | `permissions.py` 的 `model_profile` | 哪个 Agent 用哪个档位 |
| 4 · 运行时覆盖 | `--profile agent=profile` / 环境变量 | 本地调试与换档实验（E4） |

分层的收益是可组合：换云厂商不动模型选型，换模型不动 Agent 拓扑，
换绑定不动任何配置文件——**且第 3 层的改动会自动进 Worker CR**，因为 CR 由权限矩阵生成。

**凭证一律是引用而非值**：`env:` / `k8s-secret:` / `higress-consumer:` / `none:`。
配置文件因此可以安全进版本库，密钥永远不进配置、不进权限矩阵、不进 Trace。
`higress-consumer:` 对应生产路径——Worker 只持 consumer token，真实密钥留在网关侧。

四条不变量在**进程启动时**校验，违反即拒绝启动（不是运行到一半才报错）：

| 不变量 | 反向验证 |
|---|---|
| 对抗双方必须分属不同模型族 | 配成同族 → `ConfigError` |
| PII 触点的模型不得越出数据驻留白名单 | provider 挪出白名单 → `ConfigError` |
| `llm=False` 的 Agent 不得绑定任何档位 | 给 executor 绑模型 → `ConfigError` |
| 凭证只以引用形式出现 | 配置中出现密钥形态字符串 → 测试失败 |

四条都带**反向验证**：不只测「合法配置能通过」，还测「非法配置真的会被拒」。
只测正向的约束等于没有约束。

**PII 围栏值得单独说**：由于 `due-diligence` 是唯一 PII 触点，只要它绑定档位的 provider
数据驻留区在白名单内，就**静态证明**了 PII 不会流向白名单外的厂商。
这是单一全局配置根本无法提供的能力，也是银行必然会问的问题。

## 1.3 目标接口：`LLMGateway`

单一入口，中间件链固定顺序。**顺序本身是安全设计**——脱敏必须在模型路由之前，预算校验必须在发出之前。

```
InferenceRequest
  ├ task            任务类型（枚举，不接受自由字符串）
  ├ prompt_ref      提示词引用 {name, version}，由 Nacos 解析
  ├ payload         结构化输入
  ├ output_schema   JSON Schema，与 skills/<name>/schema.json 同源
  ├ policy          FailurePolicy{retries, on_exhausted, degradable}
  ├ budget          {max_tokens, max_cost_cny, max_latency_ms}
  ├ caller          调用方 Agent id（用于权限与脱敏判定）
  └ ctx             {case_id, trace_ctx, determinism{temperature, seed}}

        ↓ 中间件链

  ① PromptResolver   prompt_ref → 文本 + 确定版本号；版本号写入 Span
  ② PIIRedactor      按 schema 中标记 pii:true 的字段脱敏；
                     caller ∉ pii_touchpoints() 却携带 PII 字段 → 直接抛错
  ③ ModelRouter      按 (task, caller) 选择后端与档位
  ④ SchemaEnforcer   校验；不合规则把 validator 错误回喂做一轮修复；仍失败交 policy
  ⑤ Recorder         录制 / 回放（见 1.3 b）
  ⑥ BudgetMeter      案件级累计预算，超限降级或升级人工

        ↓

InferenceResult
  data, prompt_version, model, backend, tokens_in/out, cost_cny,
  latency_ms, attempts, repaired: bool, degraded: bool
```

`prompt_version` / `attempts` / `repaired` / `degraded` 四个字段全部进 Span——**「模型第几次才给出合规输出」本身是质量信号**，不该被吞掉。

## 1.4 三个非常规设计

### (a) 异构对抗：对抗双方必须使用不同模型族【已实现】

这曾是设计里**真正的漏洞**。

我们把 `risk-analyst` 与 `devils-advocate` 拆成两个 Agent，理由是「同一上下文内 LLM 会自洽坍缩」。但如果两者调用同一个模型、同一批权重，坍缩只是从**上下文层面**搬到了**权重层面**——同一个模型的两个实例，不是两个独立观点。它们共享相同的先验、相同的盲区、相同的幻觉倾向。

**约束的落地形式**：`config/models.yaml` 用 `adversarial_pairs` 声明对立关系，每个档位带 `family` 字段，`modelconfig.check_invariants()` 断言两者族不相交，违反即拒绝启动，并写入 Worker CR 的 `spec.llm.profile`。就像权限矩阵约束工具一样，**模型族也进矩阵**。当前绑定：定性官 `qwen-max`（族 qwen）⇄ 质疑官 `doubao-1-5-pro-32k`（族 doubao）。

这条把「目标函数对立拆分」补完了最后一环，而且**可实验验证**——见 E2-A2。如果实验显示同模型与异构模型的 pair flip rate 无差异，这条主张就该撤回。

### (b) 磁带模式：弥合 stub 与 live 的断崖【待做】

新增第三种后端 `--llm replay`。

用 live 跑一遍，把 `(task, prompt_version, payload_hash) → response` 冻结成磁带存进 `poc/cassettes/`。此后评测集用 replay 跑：**既是真实模型的真实输出，又完全可复现。**

关键约束：磁带 key 包含 `prompt_version`。提示词一改，磁带即失效，强制重录——防止提示词漂移后评测还在拿旧结论说话。

这直接回应「你的 PoC 只有 stub，等于没接大模型」的质疑，同时不让发布门禁依赖模型的当次发挥。三种后端各司其职：

| 后端 | 用途 | 可复现 | 真实模型 |
|---|---|:--:|:--:|
| `stub` | 离线门禁 · 对照组 | ✓ | ✗ |
| `replay` | **主实验与评测集** | ✓ | ✓ |
| `live` | 录制磁带 · 时延与成本测量 | ✗ | ✓ |

### (c) 影子比对：stub 作为永远在线的对照组【待做】

replay/live 模式下同时执行 stub 推理，两者结论不一致时打一条 `divergence` Span。

stub 是**用规则实现的行内口径**。模型跑偏时，这条 Span 就是告警信号。生产上 stub 不参与决策，但它是一条零成本、永不下线的对照组。这也是把「大模型不可控」这个真实顾虑落到工程上的答案。

## 1.5 三个 LLM 任务的接口契约

| task | caller | 模型档位 | 失败策略 | 允许降级？ |
|---|---|---|---|:--:|
| `risk_root_cause` | `risk-analyst` | 强模型 · 族 A | 重试 2 次 → 结论置 `INSUFFICIENT` → 回退 EVIDENCE | **否** |
| `devils_advocate` | `devils-advocate` | 强模型 · **族 B** | 重试 2 次 → 判 `INSUFFICIENT_EVIDENCE` → **阻断** | **否** |
| `report_narrate` | `compliance-auditor` | 中档模型 | 失败 → 降级为模板成文 | 是 |

这张表本身就是一个论点：**只有不影响决策的环节才允许降级。**

尤其注意第二行——质疑器失效时，fail-safe 的方向是**阻断**而不是放行。质疑器坏了就当作「无法完成质疑」，案件不得进入处置。这与 RiskGate 的 fail-safe 是同一条原则在不同层的体现。

## 1.6 兼容性

两个调用点各改一行，Span 属性改由 `gateway.span_attrs(caller)` 统一提供。

# 一·五、Prompt 与上下文工程【已实现】

## 1.7 提示词是带版本的资产，不是字符串常量

提示词此前硬编码在函数体里。后果有两个：改监管口径等于改代码；Trace 里没有
`prompt_version`，复核一个三个月前的处置结论时无法重建当时的全部输入。

现在 `prompts.py` 是注册表，每个模板带 `version` / `objective` / `changelog`，
渲染时**缺槽位与多余槽位都抛错**——渲染失败比渲染出半成品安全，
模板改了而调用方没跟上必须当场发现。版本号写入 Span。

一个刻意的结构选择：**目标函数（`objective`）单独成字段，不埋在正文里**。
对抗双方的差异就是这一句，把它拎出来才能在回归里断言「两个角色确实在做不同的事」。

## 1.8 上下文装配：三个坑，逐个用代码堵

| 坑 | 后果 | 堵法 |
|---|---|---|
| **静默截断** | 超预算时悄悄丢尾部，模型看不到关键事实却照样给结论 | 裁剪必须留痕：`manifest.dropped` 记录丢了什么、为什么丢，并进 Span |
| **原文灌入** | 裁判文书全文进上下文，既爆预算，又让「模型看的是哪一份」无法举证 | `add_evidence_refs()` **强制**只放 `evidence_id` + 抽取字段，检测到长文本直接抛错 |
| **关键块被挤掉** | 预算压力下把清单、输出契约裁掉 | `required=True` 的块不参与裁剪；必需块本身超预算则抛错，不硬塞 |

排序原则是**目标与契约在前，事实在中，参考在后**。模型对长上下文的首尾更敏感，
「你要做什么、做完的标准是什么」被挤到中段是最糟的情况。

一处值得区分的细节：**证据原文**绝不入上下文（模型要的是抽取字段，原文靠哈希锚定），
但**知识片段**的正文就是推理对象，必须入。所以后者不剥离正文，只做逐片截断且截断留痕——
默默砍掉条款后半段会让模型看不到但书和除外情形，这在合规场景里是致命的。

## 1.9 待办清单：不是提示技巧，是完成性契约

**to do list 为什么有效**：它把长程任务外化成可枚举、可检查的子项，
让模型不必靠注意力在长上下文里维持目标，从而减少遗漏、重复与提前收工。
本质是拿显式状态换注意力预算。

**但它有个根本弱点**：清单通常由模型自己维护，模型可以偷偷改、悄悄划掉。
「模型说它做完了」和「它真的做完了」是两回事。

所以我们的清单是这样的：

1. 清单由**系统**从上游产物派生，**不由模型生成**；
2. 清单块注入提示词，告诉模型完成标准；
3. 模型返回后，**由代码逐项核对覆盖**——未覆盖不是「默认通过」，而是**阻断**。

提示词里的清单只是把契约告知模型；真正起作用的是事后那次核对。

### 这堵住了一个真实的漏洞

此前质疑方可以只反驳 3 条主因里的 1 条、对另外 2 条保持沉默，
而系统无法区分「反驳失败」与「根本没看」。

> **未被质疑的主因 ≠ 质疑通过。** 前者只是没人看过。
> 把两者混为一谈，整个对抗环节就可以被静默跳过。

现在覆盖不足会让裁决判为 `EVIDENCE_INSUFFICIENT`，走已有的唯一回退边补证再议；
重试用尽即转人工。之所以不新开一条边：质疑方处理不了某条主因，最常见的原因
就是缺少判断它所需的证据，而回退带重试上限，是一条有界且 fail-safe 的路径。

两类清单都已落地，新增指标 **质疑覆盖率** 与 **取证清单覆盖率**，目标均为 100%：

| 清单 | 派生自 | 未覆盖时 |
|---|---|---|
| `rebuttal` 质疑清单 | 定性方的每条主因（置信度 ≥ 0.5） | 裁决判 `EVIDENCE_INSUFFICIENT`，回退补证 |
| `evidence` 取证清单 | 信号类型 → 该类型必须取到的事实 | 补登记为显式证据缺口，进取证清单交人工 |

第二条的意义在于：**没有它，一条本该取而未取的事实会从证据链里静悄悄消失**，
「输出取证清单交人工」这句话也就无从落地。

# 一·六、查询改写【已实现】

## 1.10 六个维度

一句自然语言检索词在合规场景里几乎必然召回不全。拆成六维子查询，各带独立过滤与权重，
融合后排序，每条命中记录它由**哪些维度**召回。

| 维 | 解决什么 |
|---|---|
| `stance` 立场 | 求证方找**构成要件与认定标准**，证伪方找**认定门槛**。对抗式设计在检索层的延伸 |
| `terminology` 术语规范化 | 行内口语 → 监管术语（抽贷→提前收回贷款，担保圈→关联客户认定）。不做这一维，业务口语几乎检不到条款原文 |
| `signal_topic` 信号主题 | 信号类型 → 绑定的条款主题。让检索由**案件事实**驱动，而非只由角色固定查询词驱动 |
| `clause_ref` 条款直查 | 事实中出现条款号时**精确召回**，不走语义——语义检索在「第十八条」这类精确引用上表现很差 |
| `negation` 否定式 | **仅证伪方**：主动检索「不构成 / 除外 / 豁免 / 不适用」。正向检索天然覆盖不到除外条款 |
| `recency` 时效 | **生效日 ≤ 案件时点** |

`matched_dimensions` 既是可解释性，也是评估改写效果的直接依据：
某一维从不贡献命中，说明那一维要么设计错了，要么词表没覆盖到。

## 1.11 时效维修复了一个真实缺陷

跑真实回溯案例时发现：`CASE-003` 的 `as_of` 是 2017-04-01，却召回了 **2025-06-01 生效**
的行内制度。这是**知识维度的前视污染**——和把后来才披露的证据放进决策时点是同一类错误，
只是更隐蔽，因为条款看起来「一直都在」。

已修复并加了三道防线：`PolicyRag` / `CaseMemory` 过滤、`tools/check_pit.py` 第 4 项检查、
以及端到端回归断言。空集时还要区分「知识库里没有」与「全被时效过滤掉了」——
两者的处置完全不同。

提示词里也明说了这件事：告诉模型它看到的条款已按时点筛过，
**不得引用任何该时点尚未生效的规定，即使它知道后来存在**。
不说清楚会有个隐蔽后果：模型发现「找不到某条我知道存在的规定」，可能凭记忆补上。

## 1.12 澄清：三条渠道，能自动的绝不问人

需要补充信息时，我们**不默认追问用户**。

> 银行场景里补充信息的成本不在用户打字，而在于「去哪个系统查、有没有查询授权、谁有权限」。
> 所以澄清的产物应当是**一张可派发的任务单**，不是一个问题。

| 渠道 | 何时用 | 例子 |
|---|---|---|
| `AUTO` | 已有明确规则可自动决定 | 流水采样不足 → 直接降为弱证据，不打扰任何人 |
| `SYSTEM_TASK` | 需要去某个系统查，人也答不上来 | 主体重名 → 派工商精确查询任务（按统一社会信用代码匹配） |
| `HUMAN_CHOICE` | 确实需要人的**业务判断** | 被担保方是否已实质出险 → Matrix room 内**选项式**提问，且阻断 |

第三条必须给选项，不问开放问题——**开放问题的回答无法结构化，也无法进证据账本**。
这一条由回归断言强制：`HUMAN_CHOICE` 渠道的澄清若没有 `options`，测试失败。

# 二、数据集方案

## 2.1 三层结构

| 层 | 名称 | 规模 | 现状 |
|---|---|---|---|
| D1 | Skill 单元级 | 886 组（其中 865 为组合遍历生成） | **已有** |
| D2 | 案件级 golden set · 合成配对 | 目标 **120 对 = 240 例** | 待建，见 §2.2 |
| **D0** | **案件级 · 真实历史回溯** | 目标 15–20 例，**现有 1 例** | 见 §2.2b |
| D3 | 对抗与鲁棒集 | 7 类故障注入 × 各 5 例 | 待建 |

**D0 与 D2 不是替代关系，是分工**：

| | D0 真实回溯 | D2 合成配对 |
|---|---|---|
| 作用 | **深度**·用于说服 | **广度**·用于统计 |
| 回答 | 「它在历史上真的提前看出来了吗」 | 「配对翻转率达标了吗」 |
| 成本 | 3–6 小时 / 例，人工整理 | 生成器批量产出 |
| 规模 | 初赛 1–3 例，复赛 15–20 例 | 120 对 |

统计指标需要样本量，1 个真实案例出不了置信区间；但路演与 PPT 主打 D0，
因为它回答评委心里那个真问题：「这东西在真实世界里管用吗」。

## 2.2 D2 的核心设计：反事实配对

**这是整个数据集方案最值得开源的部分。** `CASE-001` / `CASE-002` 已经是它的手工版本——同一主体、相同信号类型、结论相反。现在把它系统化。

每条样本是一个 **pair**：正例与负例共享主体画像与信号类型，**只在一个决定性因子上取值不同**。因子清单来自领域口径，不是拍脑袋：

| 决定性因子 | 正例取值 | 负例取值 | 绑定口径 |
|---|---|---|---|
| 涉诉实质性 | 未结案 · 我方被告 · 标的占敞口 ≥5% | 已结案 · 我方原告 · <5% | `MATERIAL_RATIO` |
| 资金对手方性质 | 穿透后为关联方 | 历史稳定供应商 | 《贷后资金用途监控》 |
| 转出金额区间 | 超出 24 月波动区间 | 落在区间内 | 行内流水基线 |
| 法代变更时点 | 与风险窗口重合 | 早于风险窗口 | 公司治理信号口径 |
| 证据完整性 | 采样完整 | 采样不足 / 主体重名歧义 | 证据等级规则 |

**配对的价值**：普通数据集只能测准确率，配对数据集能测**决策是否由正确的因子驱动**。如果系统在一对样本上给出相同结论，说明它压根没看那个因子——不管整体准确率多高，这都是失败。

由此得到本方案的**主指标**：

> **配对翻转率（pair flip rate）** = 结论正确翻转的配对数 / 总配对数。目标 ≥ 95%。

这个指标比准确率难得多，也诚实得多。它无法靠「一律报警」或「一律放行」刷分——两种偷懒策略的翻转率都是 0。

## 2.2b D0 真实历史回溯【已实现 1 例】

现有开源数据集全都用不了，这一点先说清楚，因为它比「找不到」更重要。

`ChinaZJB`（江苏某行 1329 家小微）、天池贷款违约预测、DataFountain 信用风险分类、
Home Credit——**全是 tabular 特征 → 违约标签**，服务的是评分卡与 GBDT，
正是我们开头就明确排除的场景。`CAIL` 是 268 万份**刑事**文书，主体不是企业。

更根本的是**标签性质不同**：

> 它们的标签是**事后发生的事实**（这家企业后来违约了没有）。
> 我们要的标签是**当时应当作出的决策**（在那个时点、依据那些证据，该不该压降）。
> 一家企业最终没违约，不代表当时压降额度是错的判断。

所以这个领域没有现成 benchmark，不是我们没找到，是它确实不存在——
这反过来说明我们做的数据集有开源价值。

### 三源混合，逐字段标注来源

四类证据的公开程度天差地别，因此不能一刀切地「全合成」或「全真实」：

| 证据源 | 能否取到真实数据 | 处理 |
|---|---|---|
| 涉诉、工商与治理变更 | ✅ 公开可得 | `real_public` |
| 担保关系与缓释措施 | ✅ 公开披露 | `real_public` |
| 单家银行敞口 | ❌ 从不公开 | `derived`——按公开债务规模等比推导，**保持比值不变**（判定口径本身是尺度无关的） |
| 征信报告、交易流水 | ❌ 法律禁止公开 | `synthetic`——但受真实层硬约束 |

**不是「编了一个数据集」，而是「用真实公开事件做骨架，只在法律禁止公开的两个模态上做受约束的合成」。**
评委一眼能看出哪些是真的、哪些不是、以及那两类为什么只能是合成的。

### 三条纪律

1. **只回溯已公开定论的历史事件**（已违约 / 已重整 / 已处罚 / 已结案）。
   不对当前存续且未定论的主体输出风险结论。
2. **新闻报道只用于定位案件与时间线，不进证据账本。**
   这一条是自洽的：我们自己的系统就把证据分强/弱/缺失，新闻报道恰恰是典型的弱证据。
   进账本的只能是公告原文、裁判文书、处罚决定书这类一手公开文件。
3. **无前视信息（point-in-time correctness）。** 这是最容易做错、也最致命的一点——
   整理案例时若把「后来才披露的信息」放进决策时点的证据里，系统当然能做对，但那是作弊。

第 3 条的落地方式值得单独说，因为它是「本回测无前视信息」这句话能被验证的原因：

- 每条证据带 `first_public_date`，`tools/check_pit.py` 逐条断言 `≤ as_of_date`；
- 历史结局 `retrospective_outcome` 在 `World` 构造时即被**摘出**，
  任何 Server / Skill / Agent 都取不到——是**结构约束**，不是约定或事后检查；
- 取数窗口（流水日期区间、征信比对基准日）也从案件配置读取而非写死，
  否则回测里会出现「2017 年的案子查 2026 年的流水」这种低级污染。

### 已实现：CASE-003

2017 年山东某担保圈风险传染案，`as_of = 2017-04-01`（危机公开爆发后的第一个工作日）。

- 系统判定 `RISK_CONFIRMED` · 关注类 · 净未覆盖代偿敞口达直接敞口 **2.02 倍**
- 历史结局：**31 个月**后发生债券违约（仅用于事后评分）
- 处置层级 **L3**——直接敞口 6.5 亿触发大额升档，只出方案不执行

最后一条是这个案例最有价值的地方。历史上该主体在 2017 年确有阶段性风险缓释
（共同担保人 10.27 亿 + 抵押 5.57 亿，覆盖 54.6%），所以**方向正确不等于处置正确**：
可逆的分级压降是恰当的，不可逆的立即抽贷则是过度处置。
一个真实历史案例直接验证了四维闸门这个核心设计。

## 2.3 数据来源与标签生成

三条来源，**全部不含真实客户数据**：

1. **公开可得的结构与分布** —— 裁判文书网公开文书的案由分布与字段结构、国家企业信用信息公示系统的公开登记字段、上市公司公告中的诉讼披露格式。取的是**结构与分布**，不是具体主体。
2. **因子矩阵参数化合成** —— 主体画像模板 × 2.2 的因子矩阵，笛卡尔积后按难度分层采样。
3. **LLM 辅助扩写** —— 把结构化案件扩写成自然语言：裁判文书摘要、征信报告文本、流水备注。制造真实的非结构化噪声。**扩写只改表述，不改因子取值。**

关键设计：**标签不是标出来的，是构造出来的。** 因子矩阵先确定标签，再生成数据。

- 优点：标签零歧义、零标注成本、规模可扩展——这对小团队是决定性的。
- 代价：**分布真实性弱于真实数据**。这个代价必须在方案与 PPT 里写明，不能藏。用 2.4 的验收协议部分补偿。

## 2.4 人工验收协议（不是标注，是验收）

从 120 对中随机抽 30 例，请 2 名有信贷背景的评审**独立**回答一个问题：「若你是审批人，这条应当被处置吗？」

- 与构造标签比对，计算一致率与 Cohen's κ；
- **一致率 < 90% 则判定因子口径本身与业务直觉脱节**，回去改口径，而不是改数据。

这是小团队能负担、方法论上也站得住的做法：我们不承担标注 240 例的成本，只承担验证「构造规则是否符合业务共识」的成本。

## 2.5 样本格式

JSONL，每条：

```
case_id, pair_id, factor_vector          决定标签的因子取值（可审计标签来源）
raw_sources{bureau, judicial, txn, core} 各 MCP 应返回的原文
gold{
  final_verdict,                          RISK_CONFIRMED / RISK_REFUTED / EVIDENCE_INSUFFICIENT
  grade,                                  五级分类
  expected_action_tier,                   L0–L3
  must_cite_evidence_types[]              ← 见下
}
difficulty, provenance
```

`must_cite_evidence_types` 是第二个非常规设计：**不只判结论对不对，还判它引用的证据类型对不对。结论对但引用错，算错。**

理由很直接——在银行场景里，「蒙对了」和「查清楚了」是两件事。一个引用了错误证据却得出正确结论的系统，在下一个案件上就会翻车，而且无法向监管解释。

## 2.6 开源

`creditsentry-bench`（CC BY 4.0）：120 对配对案件 + 因子矩阵 + 生成器 + 评测脚本。

这比代码更容易被引用——别人可以不用我们的 Agent，但可以用我们的数据集测他们自己的。

# 三、实验方案

## E0 口径

- **后端**：主实验用 `replay`（真实模型输出 + 完全可复现）；`live` 仅用于录制磁带与测量时延成本。
- **样本**：D2 全量 240 例 / 120 对。
- **统计**：样本量小，用 paired bootstrap（10000 次重采样）给 95% 置信区间。配对结构天然适配配对检验。
- **所有实验结果连同磁带一起提交**，任何人可离线复算。

## E1 主实验：与三条基线对比

| 编号 | 基线 | 说明 |
|---|---|---|
| B1 | 单 Agent 直判 | 一个强模型拿到全部原文，直接输出结论与处置动作 |
| B2 | 去质疑官 | 保留拓扑，删掉 `devils-advocate`，定性结论直接进闸门 |
| B3 | 纯规则引擎 | 现行行内阈值规则 |
| — | **本方案** | 完整拓扑 |

**预期结论必须诚实写在方案里**：

> B1 在「找出真风险」（召回）上大概率与本方案接近甚至持平。本方案的胜势应当出现在**误杀率、配对翻转率、证据完备率、可举证性**四项。
> **如果实验跑出来 B1 在这四项上也不差，那说明本方案的立论有问题，应当如实报告，而不是换指标。**

把这段写进方案，是为了让评委知道我们没有设计一个必赢的实验。一个不可能失败的实验，不构成证据。

## E2 消融：逐个拆掉设计主张

| 编号 | 移除什么 | 观测指标 | 检验的主张 |
|---|---|---|---|
| A1 | `devils-advocate` | 误杀率 · 配对翻转率 | 对抗质疑的边际价值 |
| A2 | **异构模型 → 同一模型** | 配对翻转率 · 质疑成立率 | **1.3(a) 的核心假设** |
| A3 | `assert_supported()` 证据约束 | 无证据结论率 | 「无证据不决策」是否只是口号 |
| A4 | RiskGate 闸门 | 不可逆动作自动执行次数（预期 0 → 非 0） | 闸门是否真的在拦 |
| A5 | **状态机路由 → LLM 自由编排** | **同输入重跑 10 次的路由一致率** · 流程违规次数 | 「为什么金融场景要状态机」 |

**A2 与 A5 是价值最高的两个**，因为它们检验的正是本方案最不寻常的两个主张。

A5 尤其关键：LLM 自由编排的「同输入重跑一致率」这个数字，是「金融场景不能用自由编排」最直接、最难反驳的证据——如果同一个案件重跑十次走出七条不同流程，可审计性就无从谈起。这个实验成本很低，说服力很高。

## E3 鲁棒性：故障注入

七类注入，每类断言的是 **fail-safe 行为**，不只是「没崩」：

| 注入 | 期望行为 |
|---|---|
| MCP 超时 | 按 failure policy 重试 → 升级人工，不得静默跳过 |
| MCP 返回部分结果 | 证据降级为「弱」，充分度下降，触发补证 |
| 主体重名歧义 | 质疑官判 `INSUFFICIENT_EVIDENCE`，阻断 |
| 证据哈希不匹配 | 该证据作废并告警，引用它的结论一并作废 |
| 越权调用尝试 | `PermissionDenied` + **被拒调用进审计日志** |
| 审批回调签名伪造 | 拒绝执行，降级 L0 |
| 执行中途失败 | 自动回滚至 rollback_point，额度恢复原值 |

本质是把已有的 36 项安全回归扩成一个可报告的实验，产出「注入 N 类故障，M 类被正确拦截」的表。

## E4 模型可替换性

同一套 prompt 与 schema 换三档模型（强闭源 / 中档 / 开源本地），报告各档全部指标与单案件成本。

目的**不是选出最好的模型**，而是证明方案不锁定单一模型——这是评分表「可替换性」的直接证据。预期结论：中档模型在配对翻转率上会明显掉，因为翻转要求识别细粒度因子；这恰好说明这个指标有区分度。

## E5 成本与时延

单案件 token / 费用 / 端到端时延，按 Span 分解到 Agent 粒度，给出「日均 2000 件预警」的推算年成本。

这一条评委一定会问，而且是唯一一个能把技术方案翻译成采购决策的数字。

## 工作量与初赛取舍

# 四、路演方案

## 8 分钟三幕

**幕一 · 90 秒 —— 抓住真风险。**
跑 `CASE-001`。屏幕左侧 Span 树实时滚动，右侧处置意见书成文。收尾动作：点开正文里的一个 `[EV-xxxx]` 角标，展开征信原文快照与 sha256。
> 一句话：结论不是模型说的，是证据链推出来的。

**幕二 · 150 秒 —— 不误杀。**
跑 `CASE-002`。强调：同一主体、同样三类信号、结论相反。逐条展示质疑官的反驳文本。
> 一句话：让 Agent 敢说「这不是风险」，比让它报警难得多。

**幕三 · 180 秒 —— 拦不住的自动执行。** 三个现场动作：
1. `--deny-approval` → L2 降级 L0，现场 diff 额度前后值，**未被修改**；
2. 把动作换成「提前收贷」→ 闸门判 L3，只出方案不执行，**当场改任何参数都不执行**；
3. 让 `risk-analyst` 去调信贷核心写接口 → `PermissionDenied`，且**被拒调用出现在审计日志里**。

**收尾 · 90 秒** —— 三条命令复现、开源清单、边界坦白。

## 最强的一招：让评委改一个字段

> 请评委任选 `CASE-001` 里的一个因子——比如把涉诉标的占敞口从 30% 改成 1%——当场重跑，系统翻案为 `RISK_REFUTED`。

这比任何一页 slide 都有说服力，因为它证明结论由证据驱动而非硬编码。

**前提**：必须提前演练，且把可改字段**限定在因子矩阵内**。现场翻车比不演示更糟。准备一张「可改字段卡片」递给评委，既显得开放，又控制了边界。

## 兜底

- 全程离线可跑，不依赖网络与云账号；
- `live` 失败自动降 `replay`，`replay` 失败自动降 `stub`；
- 预录 3 分钟视频，现场演示失败立即切视频；
- `poc/out/` 预生成全部产出文件，随时可直接打开。

## 五个必被问到的问题与答法

| 问题 | 答法 |
|---|---|
| 为什么不是一个大 Agent？ | 权限等价类推导，合并任意两个即越权；再给 B1 基线的误杀率与证据完备率数据 |
| stub 是不是等于没接大模型？ | replay 磁带是真实模型输出且可复现；E4 给三档模型对比 |
| 数据是合成的，怎么证明有效？ | 因子矩阵构造标签（零歧义）+ 人工验收协议（κ 值）+ 配对翻转率这个防作弊指标 |
| 银行凭什么敢让它自动执行？ | 865 组全组合遍历证明不可逆动作永不自动；唯一写触点；幂等 + 回滚；审批被拒即降级 |
| 和 RPA / 规则引擎差在哪？ | B3 基线数字 + 非结构化证据处理 + 经验回流；同时坦白规则引擎在确定性场景更划算 |

最后一条的坦白很重要。**承认方案不适用的地方，会让适用的地方更可信。**
