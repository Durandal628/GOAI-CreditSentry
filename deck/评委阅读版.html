01 场景与价值信衡 CreditSentry　GOAI 赛道一 · 新智基座｜Agent Infra4 / 23

场景不是选出来的，是从一条断裂的作业链上找出来的

商业银行小微与对公信贷的贷后管理环节。预警系统银行早就有了，问题出在预警之后。

① 预警产生行内预警平台 · 外部舆情 · 监管推送
② 核实取证人工逐条跨系统查
③ 风险定性人工判断
④ 出处置方案人工撰写
⑤ 审批风险经理 / 审批人
⑥ 执行与留痕人工操作 + 事后补材料

深色三段 = 本方案接管的范围。① 银行已有系统，⑤ 必须留给人——这两处刻意不碰。

目标用户是谁

主用户 · 贷后风险经理：每天面对成百上千条预警，逐条核实，处置周期以天计。

协同方 · 客户经理：只有他能向客户索取财务报表这类不在任何系统里的材料。

监督方 · 合规与内审：他们不看结论，看的是「这个结论怎么来的」。

为什么是这个场景

它同时具备三个特征，缺一不可：高频（日均千级预警）、 高摩擦（每条要跨 4 个以上系统取数）、 高后果（处置动作直接动客户额度）。

前两个决定了自动化有价值；第三个决定了不能直接放手让模型干——这正是 Agent Infra 该解决的问题形态。

我们不做什么

不做评分卡与违约概率预测——那是 GBDT 的活，做了也是重复造轮子。

不做「AI 预警」。银行的预警数量已经过剩，再加一个模型只会让噪声更多。

我们做的是预警之后那段没人管的链路。

业务价值分两层：省下来的时间，和敢不敢用

第一层是效率，容易量化但不稀缺；第二层是可举证性，难量化但决定这套系统能不能真的上生产。

第一层 · 效率（实测，可复现）

单案端到端
18 毫秒（规则推理）／接大模型时以秒计。对照：人工处置周期以天计
降噪率
50 – 62.5%（三条实测链路），且每条丢弃都可回溯
单案成本
￥0.0153；按日均 2000 件推算约 ￥31/天、￥7,628/年
自动取数
单案 30+ 次跨 4 系统调用，全部自动完成并留痕

成本口径取自真实的上下文装配结果而非经验估值；不含修复轮——该发生率要真机跑过才有实数。

第二层 · 可举证性（决定能不能用）

每个结论都能指回证据——无源结论会让报告拒绝生成，而不是打印出来。

每次分支都能说清为什么——路由决策带规则 ID 与版本，不靠日志拼凑。

越权尝试也留痕——只在成功路径留痕的系统，没法回答「有没有人试过绕过去」。

不可逆动作系统永不执行——这一条让「自动化」在信贷场景变得可谈。

行业可复制性：可迁移的是内核，不是流程

保险核赔
报案归并去重 → 单证取证 → 定损定性 ⇄ 反欺诈质疑 → 分级赔付（小额自动、大额人核）

供应链金融
贸易背景真实性核验：多源单据交叉验证 + 对抗质疑，处置动作换成放款闸门

工业设备运维
告警降噪 → 多源取证 → 根因定位 ⇄ 反驳 → 分级处置（远程复位可自主、停机必须人批）

内容与账号风控
信号聚合 → 证据固定 → 判定 ⇄ 申诉视角质疑 → 分级处置（限流可逆、封禁不可逆）

四者共享同一组骨架：信号归并 → 证据固定 → 对抗式判定 → 按可逆性分级处置 → 留痕审计。 换行业要改的是取数接口与判定口径；架构、闸门、账本、审计不动。可迁移清单见第 16 页。

协作流程：模型只做阶段内判定，不决定流程走向

金融场景要求可复现可审计，而自由编排不可复现——同一个案子重跑十次可能走出七条路径。 所以流程骨架是确定性状态机，12 条规则显式声明。

INTAKE 受理signal-hub 归并降噪 · 敞口测绘
EVIDENCE 取证due-diligence 跨 4 系统取原文并登记证据
ADJUDICATION 裁决定性 ⇄ 质疑 强制并行，质疑不可跳过
DISPOSITION 处置闸门定级；需审批档停下等人
AUDIT 审计核验生效 · 合规逐条举证 · 经验回流
CLOSED 闭环归档

三条硬约束写在路由表里，不交给模型

R-04 质疑不可跳过：取证充分后强制并行派发定性与质疑，没有「跳过」这条分支。

R-05 唯一回退边：全流程只有一条回退边，且带重试上限，不存在无限循环。

R-03 / R-12 两条转人工入口：材料不够走 R-03；证据够了但裁决反复收敛不了走 R-12。

为什么要有 R-12

R-03 只管住了「证据充分度不达标」。但裁决判证据不足时，充分度可能是达标的—— 质疑器失效、清单覆盖不全都会这样。此时回退会再次命中 R-04，形成环路。

规则推理的确定性掩盖了这个环，接真实模型后它就会出现。 这是接大模型过程中发现并补上的第 12 条规则。

可审计性的落点

路由决策本身就是一条轨迹记录，携带三个字段：路由键、命中规则 ID、规则版本。

「为什么当时走了这条分支」不是靠日志拼凑推测出来的，是直接读出来的。

12 条规则在代码与声明式配置中同构声明，测试断言两者不漂移，且每条规则都必须可被触达——死规则会让测试失败。

这一层的取舍很明确：牺牲编排的灵活性，换取整条链路的可复现与可举证。 在信贷处置场景，这个交换是划算的——灵活性带来的收益远小于「说不清为什么」带来的风险。

上下文传递：三个坑，逐个用代码堵

上下文工程最容易出问题的不是「装不下」，而是装丢了却看不出来。三条机制都留痕，不留痕的堵法等于没堵。

坑一 · 静默截断

超预算时悄悄丢尾部，模型看不到关键事实却照样给结论。

堵法：裁剪必须留痕——丢了什么、为什么丢，都记进装配账单并进轨迹。必需块不参与裁剪；必需块本身超预算则直接抛错，不硬塞。

坑二 · 原文灌入

裁判文书全文进上下文，既爆预算，又让「模型看的是哪一份」无法举证。

堵法：证据只放编号 + 抽取字段，检测到长文本直接抛错。原文靠哈希锚定，给人看不给模型看——两者本就该分开。

坑三 · 关键块被挤掉

预算压力下把清单、输出契约裁掉，模型不知道自己要做完什么。

堵法：排序原则是目标与契约在前、事实在中、参考在后。模型对长上下文首尾更敏感，把「做完的标准」挤到中段是最糟的情况。

待办清单：不是提示技巧，是完成性契约

清单之所以有效，是把长程任务外化成可枚举、可检查的子项。但它有个根本弱点：清单通常由模型自己维护，模型可以偷偷改、悄悄划掉。

所以本方案的清单是：由系统从上游产物派生 → 注入提示词告知完成标准 → 模型返回后由代码逐项核对。 提示词里的清单只是告知契约，真正起作用的是事后那次核对。

这堵住了一个真实漏洞：此前质疑方可以只反驳 3 条主因里的 1 条、对另外 2 条保持沉默，系统无法区分「反驳失败」与「根本没看」。

未被质疑的主因 ≠ 质疑通过。前者只是没人看过。

六维查询改写与澄清选路

立场（求证方找构成要件，证伪方找认定门槛）· 术语规范化（行内口语→监管术语）· 信号主题 · 条款直查（精确引用不走语义）· 否定式（仅证伪方，主动找除外与豁免）· 时效。

时效维修复了一个真实缺陷：2017 年的回溯案件曾召回 2025 年才生效的行内制度。

这是知识维度的前视污染，比证据层更隐蔽——条款看起来「一直都在」。

澄清不默认追问用户：能自动决定的自动决、能派任务的派任务、确需人判断的给选项不问开放问题。 理由很实际——银行场景补充信息的成本不在用户打字，在于去哪个系统查、有没有授权。

第一道 · 对抗式判定

定性岗与质疑岗输入完全相同、上下文完全独立、目标函数刻意对立：一个论证风险成立，一个负责推翻它。

异常分支：三条失败路径，降级方向恒为阻断

一个系统的可信度不看它顺利时的表现，看它出问题时往哪个方向倒。下面三条都是实测可复现的路径。

失败一 · 模型给不出合规输出

定性失败 → 判「证据不足」回退补证
质疑失败 → 判「质疑未完成」直接阻断

只有不影响决策的环节才允许降级。质疑器坏了不等于质疑通过—— 与闸门的失败即阻断是同一条原则在不同层的体现。

降级必须留痕：进轨迹、进日志、进指标，并在界面显式打出来。一次悄悄降级的运行和一次正常运行长得一样，那么「这个结论怎么来的」就永远说不清。

失败二 · 取证不足以定论

回退补证 ≤ 2 轮 → 仍不足 → 转人工，且必须有交付物

转人工不等于甩给人。系统放弃自动处置时的最后一个动作，是把工作交接清楚： 为什么停、已查到什么、还缺什么、每项找谁补。

待补项区分「系统能重取的」与「只能靠人要的」——财务报表不在任何可查系统内，系统重试多少次都拿不到，只能由客户经理向客户索取。这正是转人工存在的理由。

失败三 · 人工审批被驳回

L2 → 降级 L0 只读诊断，额度不被修改

审批是真的阻塞：后端线程停在那里等决策，不是走个过场的确认框。

驳回后可在取数留痕里核对——没有任何一次成功的写操作。这条由回归断言，不靠人工检查。

接大模型后新增的一层：输出契约

规则推理模式下模型输出由代码构造，字段必然齐全；接真实模型后它由模型生成，没有任何东西保证它齐全。 因此 live 路径多一层固定顺序的处理链：

传输重试限流与 5xx 退避重试；鉴权失败立即上抛
抽 JSON剥围栏与寒暄，只处理包装不猜内容
归一化吸收表述差异
结构校验枚举、区间、必填、证据引用非空
语义校验证据编号是否真实存在、清单是否逐项回执
至多一轮修复回喂错误让模型自己改
失败策略见上方三条

归一化与校验之间有条硬线：把 "62%" 改成 0.62 是纠正表述；给一条没有证据的结论编一个 ID 是伪造证据。 前者做，后者绝不做——这条线由专门的反向断言守着。

· PII 触点唯一：只有一个角色能读征信与流水
· 定性岗零工具权限（防边查边下结论）
· 执行方与审计方不是同一角色
· 编排者不持有任何业务工具
· 越权调用一律拒绝，且被拒调用进留痕
· 部署配置与权限矩阵零漂移，漂移即测试失败

执行与数据边界

· 不可逆动作在任何入参组合下都不落进自主档
· 入参缺失时降为最高管控档，而非放行
· 白名单外动作一律拒绝
· 幂等重放不重复执行；回滚可恢复原值
· 审批被拒即降级只读，额度不被修改
· 无证据 / 引用无效证据 / 仅凭缺失证据的结论一律被拒
· 原文不入模型上下文；裁剪必须留痕
· 配置文件不含任何明文密钥（按密钥形态匹配）

模型使用边界

· 对抗双方必须异构，配成同源即拒绝启动（含反向验证）
· PII 触点的模型不得越出数据驻留白名单（含反向验证）
· 无模型入口的角色不得绑定任何模型档位
· 两种推理模式产出同一套输出契约
· 归一化只吸收表述差异，绝不伪造证据引用（含反向验证）
· 模型失效时降级方向恒为阻断
· 密钥只存在本次运行的内存里，不入配置、不入任何留痕

回溯伦理边界

只回溯已有公开定论的历史事件（已违约 / 已重整 / 已结案），不对当前存续且未定论的主体输出风险结论。 新闻报道只用于定位案件与时间线，不进证据账本——这恰好符合我们自己的证据等级规则：新闻是典型的弱证据。

无前视信息由三道防线保证：每条证据标注首次公开日并逐条校验；历史结局在数据构造时即被摘出，任何环节结构上不可达；知识召回按时点过滤。

数据来源披露

合成数据 + 公开数据，不含任何真实银行客户数据。 链路 A/B 为全合成；链路 C 逐字段标注来源：担保关系与金额取自公开披露，单家银行敞口为推导值（从不公开）， 征信与流水依法不可公开故为合成。

不是「编了一个数据集」，而是用真实公开事件做骨架，只在法律禁止公开的两个模态上做受约束的合成。

一处已知的标定局限

敞口升档阈值目前对所有客户分层使用同一套绝对值。在链路 C 这类大型集团客户上， 它会把几乎所有可逆动作都推到最高档。

机制是对的，标定不对——复赛应把阈值改为按客户分层参数化。

这是跑真实案例才暴露出来的问题，如实记在这里而不是悄悄调参掩盖。

一个贯穿全文的取舍

我们在每一处都选择了牺牲灵活性换取可举证性：流程用确定性状态机而非自由编排； 裁决用纯规则而非模型；闸门在入参缺失时降级而非放行；模型失效时阻断而非尽力而为。

代价是这套系统不够"聪明"——它不会自己想出新流程，也不会在证据不足时给你一个看起来合理的结论。 但在信贷处置这个场景，这个交换是划算的。

最后一句：这套系统的价值不在于它跑得多快，而在于它出问题时往哪个方向倒。 我们把所有失败路径都调成了「停下来、说清楚、交给人」，而不是「尽力而为地跑完」。

· Manager 变厚——扩展至「贷后 + 反欺诈 + 法务」三 Team 协同

主指标：配对翻转率

同一主体、只改一个决定性因子，结论必须随之翻转。

这个指标比准确率难得多，也诚实得多—— 它无法靠「一律报警」或「一律放行」刷分，两种偷懒策略的翻转率都是 0。

如果系统在一对样本上给出相同结论，说明它压根没看那个因子——不管整体准确率多高，这都是失败。
