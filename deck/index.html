信衡 CreditSentry · 一页看懂02 / 17

让每一笔风险处置都能对监管举证

我们不做「AI 预警」。银行不缺预警系统，缺的是敢自动执行、又能担责举证的处置闭环。

我们做什么

面向银行小微与对公信贷贷后管理：从风险信号进入，到取证、定性、质疑、分级处置、合规审计与经验回流的端到端闭环。

输入：预警信号 / 征信 / 司法工商 / 流水
输出：处置意见书 + 审计报告 + 证据链

为什么难

难点不在「发现风险」，在敢不敢动手。压降额度、提前收贷都会直接影响企业经营，一旦误判即引发投诉与监管问责；而处置全程必须可追溯、可解释、可复核。

所以：既要自动化，又不能失控。

凭什么不同

① 内控即拓扑　Agent 数量由权限等价类推导，不是拍脑袋。

② 证据账本 + 对抗裁决　无证据不决策，质疑官不可跳过。

③ 执行闸门 L0–L3　不可逆动作永不自动执行。

对评委最关心问题的正面回答 ——「为什么要多 Agent，不能一个大 Agent 干完？」
因为单 Agent 在结构上无法满足金融内控的「不相容职务分离」要求。取证者不能同时定性，执行者不能同时审计。多 Agent 在本场景是合规刚需，不是技术炫技。

≥60%预警降噪率
≥85%风险定性准确率
≤2%误杀率（好客户被误处置）
100% / 0证据完备率 / 无证据结论率

场景与价值 · 核心痛点03 / 17

四个真实痛点，四条对应设计

目标用户：客户经理、风险经理、贷后管理岗、内审与合规岗。场景来源于商业银行 / 城商行 / 农商行小微与对公贷后管理的日常作业。

核心痛点本方案对应设计落点
1 风险预警数量庞大，人工筛查成本高，客户经理难以及时识别真正高风险事件 SignalHub 多源信号聚合降噪 + ExposureMapping 敞口与担保圈测绘，把海量零散信号收敛为少量带影响面的风险事件；被丢弃信号全部可回溯，杜绝静默漏丢 Skill 1·2
2 风险核查涉及工商、司法、征信、流水等多个系统，证据分散、核查耗时 DueDiligence 作为唯一取证触点，经 4 个 MCP Server 统一接入外部系统；所有原文经 EvidenceLedger 集中登记、哈希存证并评定证据等级 4 × MCP
3 贷后报告和风险处置依赖人工撰写，标准不统一，经验难以沉淀复用 能力全部 Skill 化以统一口径与 Schema；ReportCompose 自动成文并注入证据引用角标；PostmortemDistill 把已核实案件沉淀为 RiskPattern 与向量案例回流 14 × Skill
4 风险处置全过程需满足监管要求的可追溯、可解释、可复核，现有系统证据链管理不足 证据账本 append-only 不可篡改 + 全链路 Trace（含路由决策 Span）+ 执行闸门审批留痕 + ComplianceCheck 逐条举证的审计报告 证据链 + Trace

行业可复制性

本方案的可迁移资产是拓扑与契约，不是业务规则。更换 MCP 数据源与领域 Skill 后，同一套 Agent 拓扑、证据账本、执行闸门可直接平移到：

保险理赔核赔 供应链金融 反洗钱可疑交易调查 券商适当性管理 医保基金监管

数据来源与合规边界

全部使用合成数据 + 公开数据（裁判文书网公开样例、国家企业信用信息公示系统公开字段、公开财报），不含任何真实银行客户数据。企业主体、账号、金额均为构造值。

拆分判据

必须拆，当且仅当：
(i) 权限集不可安全合并（合并即越权）；
(ii) 目标函数相互对立（同上下文会自洽坍缩）。

必须合并：权限集相同 + 目标一致 + 失败策略相同。

推导结果

6 ＝ 5 个权限等价类 ＋ 1 个目标函数对立拆分

RiskAnalyst 与 DevilsAdvocate 权限完全相同，但一个求证风险成立、一个求证不成立，必须隔离上下文。

反向检验

为什么不是 4？合并即越权：取证 + 定性 → 确认偏差且 PII 触点扩散；定性 + 质疑 → 对抗坍缩；执行 + 审计 → 违反不相容职务分离。

为什么不是 10？把取证官再拆成征信 / 司法 / 流水三个，三者权限集、目标函数、失败策略完全相同，按合并判据必须合并；拆分只增跳数与 Token，不增控制力。

把《商业银行内部控制指引》的「不相容职务分离」编译成 Agent 拓扑 —— 制度即架构

Manager 是否多余？我们的诚实取舍

在单一贷后场景下，Manager 确实接近透明 —— 我们不为它编造职责。

它不可省的只有三件事：

  • 人机会话入口与实时干预
  • 多案并发时 case room 的创建、归档与超时回收
  • 跨 Team 移交 —— 涉嫌欺诈移交反欺诈 Team、需诉讼保全移交法务 Team

若砍掉它，Team Leader 需同时承担人机接口 + 领域调度 + 跨团队移交，SOUL 显著变胖；且跨 Team 就必须持有他团队权限，破坏最小权限原则。

取舍：初赛保持框架默认的极薄 Manager，复赛扩展至「贷后 + 反欺诈 + 法务」三 Team 时才变厚。

状态追踪如何映射

Case State 独立于 Matrix 消息流存储（Postgres），消息只承载事件与结论引用。房间提供人可读的协作轨迹，Case State 提供机器可查的一致性状态，两者以 case_id 关联。

多 Agent 协同 · 路由机制09 / 17

RiskCommander 如何路由：SOP 状态机，不是「智能路由」

核心原则：LLM 只做阶段内判定，不决定流程走向。金融场景要求可复现、可审计 —— 纯 LLM 自由编排不可审计，因此流程骨架必须是确定性的。

① 路由键（Routing Key）

(phase,
 signal_type,
 evidence_sufficiency,
 risk_tier,
 exposure_amount)

五元组决定下一跳。所有维度均为结构化字段，不依赖自然语言判断。

② 路由表（可灰度 · 可回滚）

声明在 Team CR / Nacos，与代码解耦。硬约束写死在表里，不交给 LLM 判断：

  • ADJUDICATION 强制并行 fan-out 给定性官与质疑官，不可跳过
  • 收敛规则：证据等级优先于置信度
  • 全流程仅一条回退边，杜绝无限循环

③ 异常路由与并发

  • Worker 超时 / 失败 → 按 Skill 声明的 failure policy 执行 retry / degrade / escalate
  • 连续失败 → 升级人类（Manager 拉人进房间）
  • 并发一致性：乐观锁 + RocketMQ 顺序消息，同一 case_id 路由至同一队列
路由决策本身就是一条 Trace Span —— 记录 routing_key、命中规则 ID、规则版本，「为什么当时走了这条分支」可举证、可回放
创新点 二 · 证据账本与对抗裁决10 / 17

无证据不决策，质疑官不可跳过

数据不完整时不编造结论，而是输出证据缺口与取证任务。这是「可举证」区别于「看起来很聪明」的分界线。

证据账本 Evidence Ledger

Evidence {
  evidence_id   : "EV-0814-0007"
  source_system : "judicial-mcp"
  snapshot_uri  : "s3://ledger/…​.pdf"
  content_hash  : "sha256:4f2a…"
  collected_at  : "2026-08-14T10:17:22Z"
  level        : "强" | "弱" | "缺失"
  level_reason  : "原文可溯源且时间窗吻合"
}

强

原文可溯源、时间窗与异常吻合、来源权威 —— 可直接支撑处置决策

弱

采样不足、间接推断、时效存疑 —— 可作旁证，不可单独定性

缺失

应有而未取到 —— 触发取证任务，不允许以推测填补

三条硬约束

  • 任何外部原文取回时强制登记，不经账本的数据不得进入决策
  • 结论 Schema 要求挂载 evidence_ids，无证据的断言被直接拒绝
  • 账本 append-only 不可篡改，报告正文自动注入证据引用角标
对抗式双轨裁决 Adversarial Adjudication

为什么必须是两个独立 Agent

LLM 强烈倾向于让自己的前后输出保持一致，因此无法在同一上下文里真诚地自我反驳。让同一个 Agent「先定性再自查」，质疑会沦为走过场。

质疑官对自动执行拥有一票阻断权：一旦判定证据不足，Case 强制回退 EVIDENCE 补证，不得进入 DISPOSITION。

对应赛题评分项「是否能处理异常、冲突和多方案选择」—— 冲突不是异常，是本方案刻意制造并加以裁决的常态。

Mock ↔ 真实：为什么零差异

Mock Server 与真实适配器实现同一个 MCP Tool 定义文件，Schema 由同一份 schema.json 生成，契约测试对两者跑同一套用例。

因此 Demo 中验证过的调用链、失败分支与幂等行为，在真实接入后语义完全一致。

权限边界与 PII 收敛

两个 PII 数据源（征信、流水）只对 DueDiligence 一个 Worker 开放。因取证触点唯一，Higress 的出站脱敏规则只需覆盖单一路径，脱敏范围可收敛、可验证。

写权限仅对 Executor 开放，且必须携带审批 token 验签。

上下文增强 · RAG 与共享状态14 / 17

RAG 四项能力全做（赛题要求至少两项）

RAG 在本方案中不是「检索增强」的装饰，而是证据链的一部分 —— 每条召回结果自动登记 evidence_id，成为可举证的决策依据。

01　Agent 记忆存储

Skill：CaseMemory

存储会话历史与决策上下文，支持时间窗查询 + 向量语义检索。作用域分 case / session 两级。

无相似案例时明确返回空集，不用低相似度结果凑数。

02　知识库 RAG

Skill：PolicyRag

面向信贷政策、监管规则、行内制度与历史处置案例，pgvector 实现向量化与相似度检索，支持按条款生效日期过滤。

召回为空时返回 no_policy_matched，绝不编造条款。

03　共享状态管理

组件：Case State Store

保存上下文、任务状态、幂等键、审批结果与证据索引。并发一致性靠乐观锁 + RocketMQ 顺序消息，同一 case_id 路由至同一队列。

与 Matrix 消息流分离存储，以 case_id 关联。

04　轨迹可观测

组件：证据账本 + OTel Trace

执行轨迹与证据链持久化，支持全链路回放与审计。审计官据此重建「谁在何时依据什么做了什么」。

账本 append-only，Trace 保留原始 Span。

「召回即证据化」—— 本方案对 RAG 的特殊约束

常规 RAG 把召回内容拼进 prompt 就结束了，结论与来源之间没有可验证的绑定关系，事后无法举证「这条结论依据的是哪一版政策」。

本方案要求：每条召回结果在进入推理上下文前，先经 EvidenceLedger 登记为一条证据，带条款出处、生效日期与内容哈希。RiskAnalyst 的结论 Schema 强制引用这些 evidence_id。

效果：报告正文的每一处政策依据都能点回原文；政策改版后可批量识别「哪些历史结论依据的是旧版条款」。

创新点 三 · 执行闸门与安全边界15 / 17

零人工不等于无限自动化

动作按 风险等级 × 证据等级 × 敞口金额 × 可逆性 四维定级。核心红线：不可逆动作永不自动执行。

L0　只读诊断

输出风险报告与建议，不触碰任何业务系统。

全自动 无需审批

典型：维持原状 + 加强监测

L1　低风险自动执行

执行完全可逆、不影响客户授信可用额度的动作。

全自动 可逆 幂等

典型：打标关注、发起补充资料通知

L2　灰度 + 审批

影响客户授信但可回滚。房间内 @ 风险经理，等审批回调验签后执行。

需审批 带回滚点 留痕

典型：额度压降、追加担保

L3　只生成方案

不可逆或影响重大的动作。Agent 永不执行，仅产出方案与证据包供人工决策。

人工决策 Agent 无执行权

典型：提前收贷、诉讼保全

安全执行五项前置条件

  • 动作白名单　白名单外动作一律拒绝
  • 幂等键　重复投递返回首次结果
  • 回滚点　执行前落 rollback_point
  • 审批验签　L2 校验 approval_token 签名
  • 双写审计　动作前后快照 + 审计流水号

Fail-safe，不是 fail-open

RiskGate 遇到任何入参缺失或规则未命中，默认降级为 L3 —— 即最保守档位，只出方案不执行。

而不是「规则没匹配上就放行」。这是安全系统与演示系统的根本区别。

RiskGate 为纯规则引擎、无外部依赖：安全判定不依赖网络可用性，也不依赖 LLM 的当次发挥。

回滚与审计闭环

回滚　执行中断按 rollback_point 自动冲正额度；回滚失败即冻结 Case 并升级人工，不做二次尝试。

审计　ComplianceAuditor 独立核验处置是否真实生效，逐条校验监管合规项，发现缺失只报告不修复 —— 审计者不得成为修复者。

在银行场景，「敢自动执行」的前提是「随时能收回」—— 可回滚性决定自动化边界，而不是模型能力
